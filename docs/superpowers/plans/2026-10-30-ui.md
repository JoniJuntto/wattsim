# wattsim UI (milestone 3a) plan

**Goal:** `bunx wattsim ui` starts one local Bun process on one port, opens the browser, and lets a person create
charge points, drive EVs and transactions by clicking, watch every OCPP frame live, inject faults, and export what
they did as a `.ws` scenario. Local-first: no auth, no users (DESIGN.md §3 "Server/UI mode").

**Stack (DESIGN.md §5):** server `packages/server` on Elysia (HTTP) + Bun WebSocket for the browser stream; never
touches OCPP sockets itself (stations own those through `@wattsim/core`). UI `packages/ui`: React 19, Vite,
Tailwind v4, shadcn, TanStack Router + Query. The built UI (`packages/ui/dist`) is served statically by the server.

## Contract between server and UI (both sides build against this; changes go through the orchestrator)

Default port 7700 (`--port`). All bodies JSON. Errors: HTTP 4xx with `{ error: string }`.

Request guard (security review, every route): a POST/PUT/PATCH/DELETE, or the `/api/stream` upgrade, whose `Origin`
header is present and is neither the server's own (`Origin` host = the request's `Host`) nor one of `--allow-origin`
is a 403. A request with a body must send `content-type: application/json` (charset allowed), else 415; a request
without a body needs none. A request without `Origin` (curl, the MCP client) is not checked for origin. The UI's
`http.ts` sends `application/json` with every body; in dev the Vite proxy forwards requests whose `Origin` is the dev
server as the API's origin (vite.config.ts), so `ui-dev` needs no flag.

```ts
type OcppVersion = 'ocpp1.6' | 'ocpp2.0.1' | 'ocpp2.1';
type EvView = { state: 'Unplugged'|'Plugged'|'Ready'|'Charging'|'Suspended'|'Full'; soc: number /*0..1*/;
                batteryKwh: number; targetSoc: number; maxKw: number };
type EvseView = { id: number; status: string /* ConnectorStatus, 1.6 vocabulary */; transactionId?: string|number;
                  idTag?: string; offeredKw: number; limitKw?: number; powerKw: number; energyWh: number /* meter register */;
                  txEnergyWh?: number /* since tx start */; ev?: EvView };
type StationView = { id: string; version: OcppVersion; csmsUrl: string;
                     connection: 'idle'|'connecting'|'open'|'closed'|'reconnecting' /* core ConnectionState */;
                     booted: boolean; evses: EvseView[]; chaos: ChaosRuleView[] };
type ChaosRuleView = { id: string; fault: string; direction?: 'in'|'out'; action?: string;
                       trigger?: string /* human text, e.g. "nth 3", "every 2", "30%" */; once: boolean; delayMs?: number;
                       detail?: string /* the fault's DSL arguments: "100ms..2s", "after 2", "-10min", "64kB" */ };
type FrameEvent = { seq: number; stationId: string; dir: 'in'|'out'; at: string /* ISO */; raw: string;
                    type: 2|3|4|5|6; id: string; action?: string /* resolved for results via pending CALL */ };
```

HTTP:
- `GET  /api/health` → `{ ok: true, version: string, persistent: boolean /* milestone 4: a data directory is in use */ }`
- `GET  /api/meta` → `{ versions: OcppVersion[], actions: Record<OcppVersion, { stationSends: string[], csmsSends: string[] }> }`
  (which actions each side initiates, for autocomplete).
- `GET  /api/stations` → `StationView[]`
- `POST /api/stations` `{ id, version, csmsUrl, evses?, vendor?, model?, heartbeatMs?, meterIntervalMs?, phases?, maxCurrentA?, voltageV?, basicAuth?, autoBoot?: boolean /*default true: connect + boot*/ }` → `StationView`.
  Bulk: `{ template: "CP-{i}", from, to, ...same }` → `StationView[]`. Duplicate id → 409.
- `DELETE /api/stations/:id` → 204 (disconnects first).
- `POST /api/stations/:id/actions` → `{ ok: true, result?: unknown }` | 4xx `{ error }`. Body is one of:
  `{type:'connect'}` `{type:'disconnect'}` `{type:'boot'}` `{type:'heartbeat'}`
  `{type:'plug', evse, ev?: {batteryKwh?, soc?, targetSoc?, maxKw?}}` `{type:'unplug', evse}` `{type:'ready'|'suspend'|'resume', evse}`
  `{type:'authorize', idTag}` `{type:'start', evse, idTag?}` `{type:'stop', evse, reason?}`
  `{type:'status', evse, status}` (Faulted / Unavailable / Available / Reserved …)
  `{type:'send', action, payload}` (raw CALL; strict validation still applies, `result` is the CALLRESULT payload)
  Behavioural faults (core `faults.ts`, milestone 4): `{type:'bootLoop', count /*0..20 reboots*/}`
  `{type:'fault', evse, code?}` (1.6: a ChargePointErrorCode; 2.x: NotifyEvent techCode, one DSL word ≤ 50 chars; default
  OtherError) `{type:'meter', op:'backwards', wh, evse?}` `{type:'meter', op:'reset', evse?}` (no evse: every EVSE)
  `{type:'reset', mode:'hard'|'soft'}`. The session export records them as `bootLoop N`, `fault evse N CODE`,
  `meter backwards 1500Wh evse N`, `meter reset`, `reset soft`.
- `POST /api/stations/:id/chaos` `{ fault, direction?, action?, nth?|every?|probability?, once?, ...params }` → `ChaosRuleView`;
  `DELETE /api/stations/:id/chaos/:ruleId` → 204. Faults and the parameters each requires (others are a 400):
  transport `drop` `delay {delayMs}` `duplicate` `corrupt` `wrongId` `callError` `noResponse`
  `jitter {minMs, maxMs}` `reorder {after?}` `halfOpen {forMs?}` `slowRead {stepMs}` (inbound only)
  `reconnectStorm {count, withinMs}`; protocol, outbound only (`direction: 'in'` is a 400): `invalidEnum {path?}`
  `missingField {path?}` (`path`: dot-joined payload path, array positions as numbers) `timestamp {shiftMs}` (signed,
  not 0) `oversized {kb}` (> 0, ≤ 1024; 1 kB = 1024 bytes). Applied as core `ChaosFaultEffect`s the way the scenario
  interpreter builds them; the session export writes the matching `chaos <fault> <args> ...` line.
- `POST /api/validate` `{ version, action, direction: 'request'|'response', payload }` → `{ ok: boolean, violations: Violation[] }`
- `GET  /api/stations/:id/frames?limit=500` → `FrameEvent[]` (ring buffer per station, 2000 frames).
- `POST /api/loopback` → `{ url }`: start (idempotent) an in-process accept-everything CSMS for trying the UI without
  a real CSMS; `DELETE /api/loopback` → 204. Reuse `FakeCsms` from `packages/core/test/fake-csms.ts`; don't duplicate it.
- `GET  /api/session` → `text/plain` `.ws` scenario recreating every station and action taken through the API, in order,
  with `wait` statements for the real gaps between actions (rounded to 1 s). Must pass `wattsim check`.

WebSocket `GET /api/stream` (server → browser only, JSON text messages):
- on connect: `{ type: 'snapshot', stations: StationView[] }`
- `{ type: 'station', station: StationView }`: after any change, coalesced to ≤ 5/s per station
- `{ type: 'removed', id }`
- `{ type: 'frame', frame: FrameEvent }`
- `{ type: 'violation', stationId, violation }` (core `Violation`)
- `{ type: 'error', stationId, message }`
- milestone 4: `run`, `run.event`, `csms`, `csms.session`, `csms.violation` (see "Server mode" below)

## Server mode (milestone 4)

Persistence is `bun:sqlite` + Drizzle (`packages/server/src/db`, SQL migrations in `packages/server/drizzle`, applied
on start). `startServer({ dataDir })` keeps `<dataDir>/wattsim.db`; without `dataDir` the database is in memory.
`wattsim ui --data <dir>` defaults to `~/.wattsim`; `--csms-port` fixes the test CSMS port (default: a free one).
Server-side types are `packages/server/src/types.ts`; the UI copy is `packages/ui/src/api/types.ts`.

```ts
type ScenarioDiagnostic = { severity: 'error'|'warning'; message: string; line: number; col: number;
                            endLine: number; endCol: number /* 1-based, endCol exclusive */ };
type ScenarioCheck = { ok: boolean; stations: number; diagnostics: ScenarioDiagnostic[] };
type SavedScenario = { id: string; name: string; source: string; createdAt: string; updatedAt: string };
type RunStatus = 'running'|'passed'|'failed'|'cancelled'|'error';
type RunSummary = { id: string; name: string; scenarioId?: string; status: RunStatus; target: 'loopback'|'url';
                    csmsUrl: string; virtual: boolean; speed?: number; seed?: number; startedAt: string;
                    finishedAt?: string; durationMs?: number /* run clock: virtual time on a virtual run */;
                    stations: { started: number; passed: number; failed: number };
                    asserts: { passed: number; failed: number }; violations: number; frames: number;
                    error?: string /* the run could not complete: scenario error, out of virtual time */;
                    recordingId?: string;
                    csms?: { reportId: string } & Tally /* virtual loopback runs: the run's own test CSMS */ };
type RunEventView = { type: 'log'; at: string; station?: string; message: string }
                  | { type: 'assert'; at: string; station: string; ok: boolean; expect: string; message?: string }
                  | { type: 'violation'; at: string; station: string; violation: Violation }
                  | { type: 'station'; at: string; station: string; status: 'started'|'finished'|'failed'; error?: string };
type RunDetail = RunSummary & { source: string; result?: { ok: boolean; durationMs: number; violations: Violation[];
                  stations: { name: string; ok: boolean; asserts: { ok: boolean; expect: string; message?: string }[];
                              error?: string; durationMs: number }[] };
                  events: RunEventView[] /* first 2000 */; eventsDropped: number };
type RecordingView = { id: string; kind: 'session'|'run'; name: string; runId?: string; createdAt: string;
                       entries: number; skipped: number /* not representable in Open OCPP Trace v1.1 */; bytes: number };
type CsmsSessionView = { identity: string; version: OcppVersion; connected: boolean; connectedAt?: string;
                         disconnectedAt?: string; connections: number; boot: 'None'|'Accepted'|'Pending'|'Rejected';
                         heartbeatIntervalMs?: number; lastHeartbeatAt?: string; statuses: Record<string, string>;
                         activeTransactions: string[]; findings: Tally; uiStation: boolean /* a UI station has this id */ };
type CsmsSummary = { running: boolean; url?: string; startedAt?: string /* identifies the instance */;
                     sessions: number; connected: number; totals: Tally;
                     byRule: Partial<Record<RuleId, Tally & { summary: string; severity: Severity }>> };
type CsmsView = { summary: CsmsSummary; sessions: CsmsSessionView[] };

```

HTTP (400 bodies for a scenario that does not parse or link are `{ error, diagnostics: ScenarioDiagnostic[] }`):
- `POST /api/scenario/check` `{ source }` → `ScenarioCheck`: parse + link, never expanding the fleet. Quirk imports
  resolve against the scenario folder, `<data>/scenarios` (the working directory without a data directory); an import
  that leaves it, symlinks included, is the diagnostic "import outside the scenario folder" and nothing is read. `use
  plugin` is a diagnostic: browser scenarios may not load server modules. A fleet over `--max-stations` (default
  10000), counted from the station ranges, is a diagnostic at the range that passes it. The editor calls it 400 ms
  after the last keystroke.
- `POST /api/scenario/format` `{ source }` → `{ source }` canonical text | 400.
- `GET /api/scenarios` → `SavedScenarioSummary[]` (newest first, ≤ 200); `POST /api/scenarios` `{ name, source }` → 201
  `SavedScenario`; `GET|PUT|DELETE /api/scenarios/:id`.
- `GET /api/runs` → `RunSummary[]` (newest first, ≤ 200). `POST /api/runs` `{ source, name?, scenarioId?,
  target?: 'loopback'|'url' /* default loopback: starts the test CSMS */, csmsUrl? /* url only; default the csms line */,
  virtual?: boolean /* default true */, speed? /* real time only */, seed? }` → 201 `RunSummary` (status `running`).
  Runs execute in process through `@wattsim/scenario` `run` (+ `driveVirtual` on a virtual clock). A virtual run with
  target `loopback` gets a test CSMS of its own on the run's virtual clock (the shared one reads the wall clock, so
  timestamps from stations that ran ahead would all be `time.skew`); it answers each BootNotification with the
  heartbeat interval the scenario set for that station, if any. It stops when the run ends; its report is saved as a
  CSMS report (`run <name> <start>`) and linked from `RunSummary.csms`. Deleting the run deletes that report. A
  real-time loopback run uses the shared test CSMS. The run uses the scenario exactly as checked (never linked again),
  refuses `use plugin` and caps the fleet. At most `--max-runs` (default 4) run at once: one more is a 429. A
  real-time run ends with status `error` after `--max-run-time` (default 1h).
- `GET /api/runs/:id` → `RunDetail`; `POST /api/runs/:id/cancel` → `RunDetail` once ended (409 when not running);
  `DELETE /api/runs/:id` → 204 (409 while running; removes its recording).
- `GET /api/runs/:id/trace` → the run's frames, `.oot.jsonl` download; `GET /api/runs/:id/junit` → JUnit XML.
- `GET /api/stations/:id/trace`, `GET /api/session/trace` → Open OCPP Trace of the kept frames (ring buffer).
- `GET /api/recordings` → `RecordingView[]`; `POST /api/recordings` `{ name?, stationId? }` → 201 (saves the session
  trace; 409 when there are no frames); `GET /api/recordings/:id` → `.oot.jsonl`; `DELETE /api/recordings/:id`.
- `GET /api/csms` → `CsmsView`; `GET /api/csms/violations?limit=1000` → `ConformanceViolation[]` (oldest first, the
  CSMS keeps 10000); `GET /api/csms/sessions/:identity/frames?limit=500` → `FrameEvent[]` as the CSMS saw them
  (station-relative `dir`, 500 per station, 404 for an unknown identity).
- `GET /api/csms/report?format=json|junit` → the live report as a download (409 when the test CSMS is not running).
- `GET /api/csms/reports` → `CsmsReportSummary[]`; `POST /api/csms/reports` `{ name? }` → 201;
  `GET /api/csms/reports/:id?format=json|junit`; `DELETE /api/csms/reports/:id`. The server also saves one when the
  test CSMS stops (`DELETE /api/loopback`, server stop) after seeing any station.

Stream additions (volume): state messages are coalesced per key to one per 250 ms like `station`.
- `{ type: 'run', run: RunSummary }`: on start, on progress (coalesced), and always once at the end.
- `{ type: 'run.event', runId, event: RunEventView }`: the first 200 per run; the rest are in `RunDetail.events`.
  Frames are not streamed (the run's trace has them; `frames` counts them).
- `{ type: 'csms', csms: CsmsSummary }`: test CSMS started/stopped, sessions and totals changed (coalesced).
- `{ type: 'csms.session', session: CsmsSessionView }`: connect, disconnect, every CALL (coalesced per identity).
- `{ type: 'csms.violation', violation: ConformanceViolation }`: at most 50 a second; past that only `csms.totals`
  moves, and the UI refetches `/api/csms/violations` while its list is behind the totals.
- No `csms.frame`: UI stations already stream their frames; the CSMS-side log of other stations is fetched (and
  polled every 2 s) from `/api/csms/sessions/:identity/frames`.

UI routes: `/scenarios?scenario=<id>&run=<id>`, `/csms?rule=<rule>&station=<id>&from=<ms>&to=<ms>` (the finding list
filtered, set by clicking the findings charts), `/csms/sessions/$identity?frame=<message id>`,
`/stations/$id?frame=<message id>&view=telemetry&window=5m|1h|6h|all` (`frame` opens and scrolls to the exchange with
that OCPP message id; `view=telemetry` shows the charts instead of the controls).

## Charts (time series, fleet aggregates, findings bins, run timelines)

The server keeps a time series per station and EVSE (`packages/server/src/series.ts`) and fleet aggregates
(`fleet.ts`); `analytics.ts` derives run timelines and findings bins from data it already stores. Types are in
`types.ts` (UI copy in `api/types.ts`):

```ts
type SeriesSample = { t: number /* epoch ms */; kw: number /* signed */; a: [number, number, number] /* A per phase */;
  v: [number|null, number|null, number|null] /* V per phase, null: not wired */; offeredKw: number; limitKw: number|null;
  soc: number|null /* 0..1 */; targetSoc: number|null; wh: number /* import register */;
  cost: number|null /* tariff cost so far: 2.1 local, else the CSMS's */; status: string };
type SeriesPoint = SeriesSample & { evse: number };
type EvseSeriesView = { evse: number; currency?: string; t: number[]; kw: number[]; a1: number[]; a2: number[]; a3: number[];
  v1: (number|null)[]; v2: (number|null)[]; v3: (number|null)[]; offeredKw: number[]; limitKw: (number|null)[];
  soc: (number|null)[]; targetSoc: (number|null)[]; wh: number[]; cost: (number|null)[]; status: string[] }; // columns
type StationSeriesView = { stationId: string; from: number; to: number; step: number /* ms, 0: every sample */;
  fullResolutionFrom: number|null /* before it, samples were downsampled */; evses: EvseSeriesView[] };
type ScheduleView = { stationId: string; evse: number; from: number; durationMs: number; ratedKw: number; profiles: number;
  periods: { startS: number; kw: number; phases?: number }[] };
type FleetBin = { t: number; kw: number; stations: number; connected: number; counts: number[] /* FLEET_STATUSES order */ };
type FleetSeriesView = { from: number; to: number; step: number; binMs: number; statuses: string[]; t: number[]; kw: number[];
  kwMin: number[]; kwMax: number[]; stations: number[]; connected: number[]; counts: number[][] /* [status][bucket] */ };
type FleetStationsView = { from: number; to: number; step: number; metric: 'power'|'status'; statuses: string[];
  rows: { id: string; energyWh: number; values: (number|null)[] /* mean kW, or a statuses index */ }[] };
type RunTimeline = { runId: string; from: number; to: number /* the run's clock */; truncated: number;
  lanes: { station: string; from: number; to: number; result: 'passed'|'failed'|'running';
           statuses: { evse: number; from: number; to: number; status: string }[];
           transactions: { evse: number; id: string; from: number; to: number; open: boolean }[];
           marks: { at: number; kind: 'assert'|'violation'|'failed'|'error'; text: string }[] }[] };
type FindingsBinsView = { from: number; to: number; step: number; t: number[]; rules: string[] /* most first */;
  byRule: number[][] /* [rule][bucket] */; errors: number[]; warnings: number[]; stations: string[];
  matrix: number[][] /* [station][rule] */; severity: Record<string, 'error'|'warning'>; total: number };
```

Sampling: every EVSE is sampled on each `meter`, `status`, `transaction` and `state` event of its station, from the model
(energy and SoC extrapolated like `EvseView`), so the series follows meter steps and every state change. Per-phase power
is `a × v / 1000` (not stored). A sample equal to the previous one is not stored (an idle EVSE costs nothing); one within
250 ms of the previous with the same status replaces its values and keeps its time, so a burst stores at most four rows a
second. Retention per EVSE: every sample of the last 6 h (at most 1024); older samples (or the oldest when the ring is
full) move to a coarse tier that keeps the lowest- and highest-power sample per 5-minute bucket (at most 432, 18 h);
beyond that they are dropped. Downsampling a query is the same min-max rule per `step` bucket, so spikes and dips to
zero survive at every zoom; ties go to the more severe status (a Faulted at 0 kW over an idle 0 kW).

Memory: a stored row is 61 bytes (time float64, 13 float32 values, a status byte) in typed arrays grown by doubling.
Per EVSE at most 1456 rows, 88.9 kB; an idle EVSE 0.5 kB; one charging all day at the default 60 s meter interval about
57 kB. Per station with two EVSEs: about 1 kB idle, 115 kB after a day of charging, 178 kB at most. At 1000 such
stations: 1 MB idle, about 115 MB after a day of continuous charging, 178 MB at most. The fleet aggregate is fixed:
8640 bins of 60 bytes, 518 kB, whatever the fleet size. The browser keeps streamed points only for stations a view is
showing (at most 3000 per EVSE) and 6 h of fleet bins.

HTTP (`from`/`to` are epoch ms or ISO dates, default the last hour; `step` ms; a bad value is a 400):
- `GET /api/stations/:id/series?from&to&step` → `StationSeriesView`: samples in [from, to] plus the one in force at
  `from`, min-max downsampled to `step`; a `step` that would give more than 2000 buckets is raised (and returned).
- `GET /api/stations/:id/schedule?evse=1&duration=86400` → `ScheduleView`: the composite schedule from now
  (`ProfileStore.composite` in W, as GetCompositeSchedule would answer), `duration` in seconds (1..7 days), `evse=0` the
  grid connection.
- `GET /api/fleet/series?from&to&step` → `FleetSeriesView`: 10 s bins (24 h kept) merged to `step`: mean, min and
  max power and mean EVSEs per status.
- `GET /api/fleet/stations?from&to&bins=120&metric=power|status` → `FleetStationsView` (heatmap rows, bins ≤ 500): per
  station the time-weighted mean power or the most severe status per bin, and the energy it delivered in the window.
- `GET /api/csms/findings/bins?from&to&step=60000` → `FindingsBinsView` over the test CSMS's kept findings (empty when
  it is not running; `step` raised to at most 500 buckets).
- `GET /api/runs/:id/timeline` → `RunTimeline`: lanes from the run's frames (the live recorder, or its saved
  recording) and events, at most 500 stations.

Stream additions:
- `{ type: 'series', stationId, points: SeriesPoint[] }`: coalesced like `station` (one message per station per
  200 ms carrying every point since; at most 500 held per station).
- `{ type: 'fleet', bin: FleetBin }`: every 10 s.

UI: the station page's Telemetry view (one panel per EVSE: power with offered and limit, current and voltage per phase,
SoC with its target, energy, running cost when priced, a status band, and the schedule ahead; crosshair synced across
every panel; window 5 min / 1 h / 6 h / all); an analytics strip above every message log (messages per bin by action,
CSMS response time p50/p95/max per action, CALLERRORs and violations per bin; clicking filters the log); fleet charts
(total power, EVSEs by status, a stations × time heatmap of power or status on canvas, top stations by energy); CSMS
charts (findings by rule or severity over time, a stations × rules heatmap, severity split; clicking filters the finding
list); the run panel's swimlane timeline. Charts are hand-built SVG and canvas, no chart library. Color: single series
and references are ink (`--chart-ink`, `--chart-ref`); state is the `--st-*` fills; nominal categories (actions, rules,
phases L1–L3) take `--cat-1..5` in that fixed order, validated for color-vision deficiency in both themes; magnitudes in
the heatmaps are one hue mixed into the card (`--seq-power`, `--violation`). Every chart has a table view. `?mock`
generates plausible series for all of them; `?mock&fleet=1000` adds 1000 quiet stations for the heatmap.

## Sites: the DLM test environment

The Site page shows how electricity flows through an electrical site and how its DLM decides. A site is a scenario
run's `site` block while it runs (then its stored report), a **sandbox** built from DSL whose EVSE leaves are bound to
UI stations, or an uploaded `--site-report` file. Server: `packages/server/src/sites.ts` (live sites, stream),
`site-sandbox.ts` (DSL to a site plan), `site-infer.ts` (an external DLM's allocation, inferred). Wire types are in the
sites section of `types.ts`; the UI copy is `packages/ui/src/api/site-types.ts` (it also copies the `@wattsim/grid` /
`@wattsim/site` shapes the wire carries: `NodeState`, `NodeInfo`, `SiteDescription`, `Allocation`, `DlmScore`,
`SiteReport`).

```ts
type SiteKind = 'run' | 'sandbox' | 'upload';
type AllocationView = Allocation /* @wattsim/site, numbers rounded to 0.01 */ & { reason: AllocationReason | 'profile';
  inferred?: true /* rebuilt from the profiles the stations received: an external DLM */ };
type SiteSummary = { id: string; name: string; kind: SiteKind; live: boolean; runId?: string; createdAt: string;
  start: number; end?: number /* epoch ms on the site's clock */; controller: 'reference'|'none' /* ever reference */;
  nodes: number; leaves: number; trips: number; peak?: { nodeId: string; pct: number }; fairness?: number };
type SiteTopology = { description: SiteDescription; nodes: NodeInfo[]; leaves: LeafInfo[] };
type SiteScoreView = Omit<DlmScore, 'evse'>;
type SiteLive = { seq: number; t: number; nodes: Record<string /* '@supply' too */, NodeState>; imbalanceA: number;
  leaves: LeafSnapshot[]; next: NextEvent | null; controller: 'reference'|'none'; score: SiteScoreView;
  violations: GridViolation[] };
type SiteDetail = SiteSummary & { topology: SiteTopology; state?: SiteLive /* live sites */;
  bindings?: Record<string /* leaf */, string /* UI station */> };
type SiteEventView = TripEvent | RecloseEvent | { type: 'violation'; t: number; phase: 'start'|'end'; violation };
type SiteReportView = SiteReport /* the --site-report file */ & { inferred?: AllocationView[] };
```

The report is **version 2** from `@wattsim/site` (version 1 files still upload and replay): `allocations` holds the
controller's keyframes only and `allocationSteps` one entry per kept step (a keyframe index or an `AllocationDelta`).
The server reads it only through `decodeAllocations` (stored) or the runtime's `allocationsSince` (live), and the UI
never decodes it: it takes every step, decoded, from `GET /api/sites/:id/allocations`. A step carries what the decision
panel shows about why an EV got less: `AllocationPhase.reservedA` (current reserved for EVSEs the controller cannot
steer) and `.overshootA` (measured overshoot taken off the budget); `AllocationEvse.confirmedA` (last accepted),
`.pendingA` (sent, not answered), `.held` (new target not sent yet) and `.capped` (capped near its draw);
`Allocation.uncontrolled[]` (`why`: offline, unknown, refused, overdraw; `reservedA`), and the reason `answer`.

An **inferred allocation** (no reference controller running): whenever a station receives a SetChargingProfile or
ClearChargingProfile, and every 10 s of site time while EVs charge, the server reads each EVSE's limit in force
(`ProfileStore.limitDetail`) and the site state: per rated node and phase the budget is rating minus the non-EV
current (as a phasor, no margin), an EVSE's allocation is its limit in force (W divided over its phases; its rating
when unlimited), a node's allocation is the sum through it, negative headroom is over-allocation, and an EVSE is bound
by the node phase above it with the least headroom. EVSEs without supply (tripped upstream) are left out.

HTTP (same guard as everything else: JSON only, same origin; request bodies at most 8 MiB, an uploaded report 64 MiB,
else 413; a site may have at most 500 EVSE leaves, `ServerOptions.maxSiteLeaves`, to be built, uploaded or shown):
- `GET /api/sites` → `SiteSummary[]` (live first, then stored, newest first, ≤ 200 stored).
- `POST /api/sites` `{ source /* ≤ 256 kB: a site block + station blocks with site ... at lines */, name?,
  controller?: 'reference'|'none' /* default: the block's controller line, else none */, bind?: Record<leafId,
  stationId>, create?: boolean /* default true: a UI station per unbound leaf, on the test CSMS */, version? }` → 201
  `SiteDetail`. A source that does not parse, link or wire is a 400 `{ error, diagnostics }`; a station bound to
  another live sandbox is a 409. Station ranges need literal bounds. Load profiles resolve like scenario imports.
- `POST /api/sites/reports` (a `SiteReportView` JSON, version 1 or 2) → 201 `SiteSummary` (kind `upload`); shape,
  description (`validateSite`), column lengths, keyframe indexes of `allocationSteps` and the leaf cap are checked (400).
- `GET /api/sites/:id` → `SiteDetail`. `GET /api/sites/:id/report[?download]` → `SiteReportView` (live: so far).
- `GET /api/sites/:id/series?from&to&nodes=a,b` → `SiteSeries` window (plus the point in force at `from`).
- `GET /api/sites/:id/allocations?from&to&limit` (≤ 20000) → `AllocationView[]`: every step decoded (reference and
  inferred, by time); the page loads its whole history from here.
- `GET /api/sites/:id/events` → `{ events: SiteEventView[]; violations }`.
- `POST /api/sites/:id/actions` (live only, else 409) → `SiteLive`: `{type:'trip', node, phases?}`
  `{type:'reclose', node}` `{type:'load', node, watts}` | `{type:'load', node, on}` `{type:'controller', mode}`. An
  unknown node is a 404, one the runtime refuses (not protective, not a load) a 400. A sandbox records each as DSL in
  the session export (`trip "Q1"`, `reclose "Q1"`, `load "HVAC" set 20kW`, `load "Heater" on`, `controller none`, in
  the first bound station's block), and the export carries the `site` block and every bound station's
  `site ... at` line (with the phase mapping it got, not `rotate`).
- `POST /api/sites/:id/stop` → `SiteSummary`: stop a sandbox and keep its report (409 for a run's site).
- `DELETE /api/sites/:id` → 204: stop a sandbox without keeping it, or delete a stored report (409 for a live run).
- Runs: `StartRun.siteController?: 'reference'|'none'` overrides the site block; `RunSummary.siteId` links the run's
  site. Deleting a run deletes its site report. UI runs serve the site's Modbus meters on free ports
  (`RunOptions.siteModbus: 'free'`), and so do sandboxes, so two runs of the same site can run at once.

Stream additions (per site, all live sites; the UI keeps them only for sites a view watches):
- `{ type: 'site', siteId, seq, t, full, nodes, leaves, imbalanceA, next, controller, score, violations }`: the nodes
  (`NodeState`, rounded) and leaves that changed since message `seq - 1` (all when `full`), coalesced to one per
  250 ms. A client whose state is not at `seq - 1` drops it and refetches `GET /api/sites/:id`.
- `{ type: 'site.allocation', siteId, allocation: AllocationView }`: every step, at most 10 a second per site.
- `{ type: 'site.event', siteId, event: SiteEventView }`: trips, reclosures, violations; at most 50 a second.
- `{ type: 'site.summary', site }`: created, changed (once a second), finished. `{ type: 'site.removed', id }`.

Persistence: migration `0002_site_reports` adds `site_reports` (summary columns + the `SiteReportView` JSON) and
`runs.site_id`. A run's site report is saved when the run ends; a stopped sandbox's too.

UI: `/sites` (list, new sandbox, upload a report) and `/sites/$siteId?node=<id>&phase=L1|L2|L3|N` (lazy chunk):
- single-line diagram laid out automatically (`lib/sld-layout.ts`): line weight by current, moving dashes by power
  (upwards for export; static arrows under reduced motion), colour by loading (`--load-ok|near|over|dead`: above 80 %,
  above 100 %, de-energised), ratings, per-phase current and thermal gauges on devices, tripped devices drawn open with
  everything downstream greyed; crowded boards fold their chargers into a group with an aggregate (expandable);
- the DLM decision panel per step: a waterfall from a node phase's rating (margin, other loads or PV, current reserved
  for unsteered EVSEs with one segment each and its reason, overshoot) to the budget, split per EVSE, with headroom;
  per-EVSE allocation against draw with the last accepted limit, marks for pending (→), held (◷), capped (⌃), below
  allocation (○), fewer phases (½) and paused (‖); the unsteered EVSEs with why and what is reserved; prev/next or
  follow live; "inferred" for an external DLM;
- the timeline per constrained node (rating, flowed, planned; profile ticks, near-trip and trip flags), click to move
  the replay; the scrubber (play ×10/×60/×300) drives diagram, decision panel and timeline together;
- the DLM score card with a one-sentence reading; controls (trip/reclose, set a load, toggle the controller).
`?mock` adds a live depot under the reference controller and a finished controller-off depot that trips
(`?mock&chargers=50` for the large case).
