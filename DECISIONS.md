# Decisions

Append-only log. One entry per decision that a future reader would otherwise have to reverse-engineer.

## 2026-10-29 Project agreed

See DESIGN.md for the full agreement from the initial design session. Key calls: Apache-2.0, Bun, custom DSL over YAML, generated Zod from verbatim-vendored OCA schemas with generated code never committed, native Bun WebSockets in the OCPP hot path, local-first server with no auth.

## 2026-10-29 Hand-written recursive-descent parser for the DSL

Milestone 1 uses a hand-written lexer and parser rather than a grammar generator. The TextMate grammar for editor support will be derived when the VS Code extension is built; until then the syntax has one source of truth (the parser) and one test suite.

## 2026-10-30 A plugged EV requests energy as soon as a transaction starts

`Station.startTransaction` (and remote starts) move an EV in IEC 61851 state B to state C automatically. A real EV asks for power the moment the EVSE offers it; scenarios that want an EV that refuses use `ev suspend`. Before this, a scenario had to write `ev ready` after every `ev plug` or the transaction sat in SuspendedEV at 0 Wh.

## 2026-10-30 The meter keeps running while disconnected

`Station.disconnect()` stops the heartbeat but not the meter timer. A physical meter counts regardless of connectivity, and the MeterValues produced offline queue in the Connection and flush in order on reconnect. The interpreter no longer has to tick the station itself during `net drop`.

## 2026-10-30 Generated Zod drops JSON Schema `default` before conversion

`json-schema-to-zod` treats any property with a `default` as required. Thirteen 2.0.1 schemas (MeterValues, TransactionEvent, GetVariables, SetVariables, NotifyReport among them) would have rejected valid payloads. The generator strips `default` as a keyword, never as a property name, and the Ajv oracle test exists to catch this class of drift.

## 2026-10-30 A station-wide Max profile is one cap shared equally by the charging EVSEs

A `ChargePointMaxProfile` / `ChargingStationMaxProfile` (and `ChargingStationExternalConstraints`) installed on evseId 0 limits the whole grid connection, not each EVSE. `ProfileStore.limitAt` divides it equally across the EVSEs with an active transaction at `t`, counting the EVSE being asked about even when it is idle, so an idle EVSE reports what it would get if it started now. The split is re-evaluated whenever a transaction starts or ends. Equal shares are simpler than a real load balancer and are deterministic; capacity an EV leaves unused (full battery, low max current) is not redistributed. GetCompositeSchedule reports the EVSE's physical limit where no profile applies, and for evseId 0 the sum of the EVSE limits capped by the station-level profiles.

## 2026-10-30 A chaos delay composes with the other chaos faults

`ChaosEngine` stays first-match-wins, except that a `delay` rule no longer ends the search: a frame takes the first matching delay rule and the first matching rule of any other fault, in whatever order they were declared, and is held for the delay before the other fault applies. Before this, `net delay` (a delay rule for every frame) silenced every `chaos` rule declared after it. Making delays compose in both directions, rather than only with rules declared later, means the declaration order of `net delay` and `chaos` lines does not matter. Delays do not add up: a second matching delay rule is not evaluated.

## 2026-10-30 Scripted `on` replies have no side effects

`Station.interceptCall` answers an inbound CALL before the version adapter, and the adapter's `after` step (the reset, the remote start) does not run. A scenario that answers `Reset` with Accepted and wants the station to reset writes that behaviour itself. The reply goes through the same strict-mode check as built-in replies, so a schema-invalid scripted reply is sent and reported as a violation; a CALLERROR code the OCPP version does not define is rejected when `on` runs instead, because the station would otherwise send an error frame no validator looks at.

## 2026-10-30 1.6 SmartCharging limits: stack level 8, 24 periods, 10 profiles

The 1.6 station advertises `ChargeProfileMaxStackLevel` = 8, `ChargingScheduleAllowedChargingRateUnit` = `Current,Power`, `ChargingScheduleMaxPeriods` = 24 and `MaxChargingProfilesInstalled` = 10, all read-only, and SetChargingProfile answers Rejected for a stackLevel above 8, a schedule with more than 24 periods, or an install that would leave more than 10 profiles (a profile it replaces does not count). The spec sets no defaults. These values are in the range AC wallboxes commonly report, 24 periods fits an hourly day schedule, and small limits make a CSMS that ignores them fail in testing rather than in the field. They are constants in `SMART_CHARGING_16`, not per-station configuration, until a scenario needs to vary them. The remote-start TxProfile is not checked against them.

## 2026-10-30 Scenario errors found when a run starts are ParseErrors

Duplicate station names across blocks, a range bound `let` that is not an integer and an inverted range depend on `let` values, so `run` finds them before creating any station rather than the parser. `run` rejects with a `ParseError` carrying the line and column, and `wattsim run` prints `file:line:col: message` and exits 2 like a syntax error. Literal duplicate names and template names that ignore their loop variable are caught by the parser.

## 2026-10-30 A composite schedule never reports a limit before it is in force

GetCompositeSchedule periods start on whole seconds from the request, but profile boundaries need not. A rise is reported at the next whole second at or after it, a drop at the whole second at or before it, so for every reported second the real limit is at least the reported one: a CSMS that trusts the composite never overloads the station. An A composite gives each period the `numberPhases` of the schedule period that sets the limit (the station's phases where none is given, or where the EVSE's rated power binds).

## 2026-10-30 The MCP server uses `@modelcontextprotocol/sdk` 1.32.2 with the repo's zod 4

`packages/mcp` depends on `@modelcontextprotocol/sdk`, pinned at 1.32.2, the current release of the v1 line. It provides the MCP framing, the stdio transport and an in-memory transport pair for tests, which would otherwise be a JSON-RPC implementation of our own. The SDK has also been published as v2 under split package names (`@modelcontextprotocol/server`, `/client`); the v1 package is still maintained alongside it, is the one the milestone plan names, and both lines speak the same protocol, so a later move is contained in `packages/mcp`. The v1 SDK declares `zod` `^3.25 || ^4.0` and reads tool schemas through `zod/v4` internally, so the tool input schemas use the workspace's zod 4 from the catalog and the install resolves one zod copy (a second copy is what causes the SDK's known TS2589 type-depth errors).

## 2026-10-30 MCP `run_scenario` ignores the scenario's `csms` line

Without a `csmsUrl` argument, `run_scenario` runs against the embedded test CSMS (`POST /api/loopback`) even when the scenario has a `csms` line. An agent can then run any example with no setup, and the file's URL usually points at a CSMS that exists only on its author's machine. Passing the URL from the file as `csmsUrl` restores `wattsim run`'s behaviour. It runs on the virtual clock by default with the CLI's 24 hour cap; a wall-clock run is aborted after `timeoutSeconds` (default 300) so a tool call cannot hang the agent.

## 2026-10-30 The CSMS checker keeps station state across reconnects and grades by spec wording

`@wattsim/csms` keeps a station's boot status, transactions and heartbeat interval for as long as the CSMS runs, not per WebSocket connection: a 1.6 charge point does not send BootNotification after a network drop, so a per-connection checker would flag every message after a reconnect. Only message ids, the in-flight CALL and pending CSMS CALLs are per connection. A station that returns with another subprotocol starts from scratch. Severity follows the spec's wording: `error` for SHALL / MUST, `warning` for SHOULD (OCPP-J one CALL in flight, 1.6 requests while Pending) and for heuristics (clock skew over 5 min, Heartbeats under half the interval apart, a seqNo gap).

## 2026-10-30 Recordings use the Open OCPP Trace Format v1.1, validated by a Zod mirror of its schema

The format DESIGN.md names exists: https://github.com/open-ocpp-trace/specification, one JSON record per message (`schemaVersion`, `timestamp`, `direction`, `messageType`, `messageId`, `action`, `payload`, `raw`, `error`, `meta`, ...). The schema, fixtures and conformance tests are Apache-2.0 and the prose is CC-BY-4.0; the prose definition of v1.1 still lives in shiv3/ocpp-cp-simulator `docs/concepts/trace-format.md`. `packages/trace/schemas/open-ocpp-trace` vendors the schema, the 16 conformance fixtures and the license verbatim from commit `c9c2499`. `@wattsim/trace` validates records with a hand-written Zod mirror of the schema rather than Ajv at runtime, so it adds no runtime dependency. Ajv stays a devDependency: the tests check that Zod and Ajv agree on every rule of the schema and that the reader reproduces each fixture's `expected.json` consumer view. The reader refuses a `schemaVersion` whose major is not 1, as the format's versioning rules require. wattsim's own fields go under `meta.wattsim` (`decodeError`, `chaos`, `injected`), and other producers' `meta` survives a read and write. Correlation inside wattsim adds one condition to the format's rule, the same `chargePointId`, so a trace that mixes charge points correlates per charge point.

## 2026-10-30 Frames v1.1 cannot carry are left out of Open OCPP Trace files; wattsim's frames lines keep everything

v1.1 requires `messageType` to be CALL, CALLRESULT or CALLERROR. It has no record for text that is not an OCPP-J array (upstream lists malformed frames as an open question) or for the 2.1 message types CALLRESULTERROR and SEND. The writer leaves such frames out, counts them (`Recorder.skipped`) and the proxy CLI warns. Writing a record that fails the schema would break every conformant consumer, and inventing a messageType would misreport the frame. A frame that is an OCPP-J array but fails decoding (unknown action, wrong arity, a 37-character id) is written with its decode error in `meta.wattsim.decodeError`. The frames line `{ts, dir, identity, version?, frame}` that the reader imports is wattsim's own format, not a standard. `--format frames` writes it for recordings that must keep every message. `dir` is station-relative (`out` = charge point to CSMS), as in core `frame` events and DSL chaos rules.

## 2026-10-30 The proxy records what each endpoint sent; chaos is noted, not recorded as the result

The proxy records every frame as its sender sent it, before chaos, with the matching rule in `meta.wattsim.chaos`. A dropped frame is in the trace and the frame a `corrupt` rule mangled appears intact. The trace then shows what the charger and the CSMS each did, which is what replay and quirk derivation need. A frame the proxy makes up itself (the CALLERROR a `callError` rule sends back for a CALL) is recorded with `meta.wattsim.injected`, and replay and `toScenario` skip it. Chaos counters are per connection on the CLI, one `ChaosEngine` per charger seeded from `--seed` and the identity as in `wattsim run`. Frames that do not decode bypass chaos, because `ChaosEngine.decide` needs a decoded frame.

## 2026-10-30 Replay matches CSMS frames by action and order, ignoring timestamps and CSMS-assigned ids

Replay sends the station's frames verbatim, keeping the station's CALL ids, and treats each recorded CSMS frame as an expectation. A CSMS CALL matches the first live CALL of the same action not matched yet, so a CSMS that interleaves differently still matches. A response matches by the id of the station CALL it answers. Payloads go through scenario's `partialMatch` after both sides drop the keys `id`, `transactionId`, `requestId`, `remoteStartId`, `reservationId` and `chargingProfileId` and have every ISO 8601 timestamp string replaced by a placeholder: these change on every run and say nothing about whether the CSMS behaves the same. A CALLERROR compares by code only. The station's answer to a CSMS CALL is re-addressed to the live id and is not sent when the live CSMS never sent that CALL. Live CALLs the trace does not have are reported and left unanswered, since answering them would add traffic the trace never had.

## 2026-10-30 `toScenario` reproduces the station's traffic, not its behaviour

A converted trace uses the DSL primitives only where they send exactly the recorded message and nothing else the trace lacks: `boot`, `heartbeat` for an empty Heartbeat, and `authorize` when the payload is what the station would build. Everything else, transactions included, is `send` with the recorded payload. `start`/`stop` would add MeterValues and StatusNotifications the station generates itself and would need an EV model the trace does not describe. `boot` sends a StatusNotification per EVSE once Accepted, so the matching StatusNotifications right after an Accepted boot are left to it and `evses N` is set. `heartbeat 24h` keeps the station's own heartbeat timer quiet: the configured interval wins over the CSMS's. The station's answers to CSMS CALLs become one-shot `on` handlers in arrival order, which have no side effects, so a recorded Accepted RemoteStart does not start a transaction the trace shows separately. Expected payloads drop the same ids and timestamps as replay. The result runs: the test converts a recorded 1.6 session, runs it against FakeCsms and gets the same CALL sequence.

## 2026-10-30 X.509 through `@peculiar/x509` 1.14.3; TLS through Bun's own WebSocket and `Bun.serve`

`packages/pki` depends on `@peculiar/x509` 1.14.3 and on `@peculiar/asn1-ocsp`, `@peculiar/asn1-schema` and `@peculiar/asn1-x509` 2.11.1, all pinned exactly. Bun's `crypto` (WebCrypto and `node:crypto`) generates and exports keys and parses certificates, but it cannot build a PKCS#10 CSR or sign an X.509 certificate, and the security profiles need both. `@peculiar/x509` runs on WebCrypto and has no native code. 1.14.3 is the last 1.x release. 2.x stopped importing its `reflect-metadata` polyfill, so every entry point would have to import it, and 3.x was three days old. The asn1 packages are the versions 1.14.3 resolves to; asn1-ocsp builds a real, signed RFC 6960 response for `GetCertificateStatus`. Core loads `@wattsim/pki` with a dynamic `import()` on the first certificate operation, so a profile-1 fleet never loads it (the 1000-station perf run stays at about 1.5 s).

Probed on Bun 1.4.4: the client `WebSocket` accepts `tls: { ca, cert, key, rejectUnauthorized }`. A wrong CA fails the handshake ("unable to verify the first certificate", "self signed certificate in certificate chain"). `Bun.serve({ tls: { requestCert: true, ca } })` enforces mutual TLS: a client without a certificate gets `TLSV1_ALERT_CERTIFICATE_REQUIRED`, and one from an untrusted CA gets "Connection ended". `Bun.serve` does not expose the peer certificate to `fetch` or the WebSocket handlers; `node:tls` does (`getPeerCertificate()`), so a CSMS that must match the certificate CN against the identity needs `node:tls`. The station tells failures apart (`HandshakeError.kind`) by these message texts and HTTP 401, which a Bun upgrade can change; `security-unit.test.ts` pins the texts.

## 2026-10-30 Security events start with security state; SetNetworkProfile applies at once

A station sends SecurityEventNotification only once it has security state: from the start when `StationConfig.security` is set, otherwise from the first certificate or security message it handles. Profile-1 stations configured as before send exactly the messages they sent before. Events raised before the first Accepted boot, or during a reboot, wait for the boot, and events raised while offline queue. A failed handshake is reported once per run of failed attempts, not once per retry. The station raises StartupOfTheDevice (first boot), ResetOrReboot, ReconfigurationOfSecurityParameters, InvalidCsmsCertificate, FailedToAuthenticateAtCsms (a refused client certificate or HTTP 401), InvalidChargingStationCertificate, InvalidFirmwareSigningCertificate and FirmwareUpdated, using the 1.6 Whitepaper names on 1.6. It does not raise SettingSystemTime, because the station never sets its clock from the CSMS.

An accepted 2.x SetNetworkProfile takes effect immediately, as if the CSMS had also put the slot first in `NetworkConfigurationPriority` and reset the station. The station reconnects with the new URL and profile and sends a BootNotification (reason `Unknown`) when the URL changed. If that one attempt fails, it goes back to the previous URL and profile. 1.6 `ChangeConfiguration SecurityProfile` does the same; the 1.6 key carries no URL, so the station uses `security.upgradeUrl`, or the current URL switched to `wss://`. Both are upgrade-only. A lower profile is Rejected, and so are profile 2 or 3 without an installed CSMS root certificate and profile 3 without a station certificate. Profile 3 sends no basic auth header.

## 2026-10-30 Certificate store rules and hash data encoding

`CertificateHashData` hashes (SHA-256 by default) are lower-case hex. `issuerNameHash` covers the DER issuer name. `issuerKeyHash` covers the issuer's `subjectPublicKey` BIT STRING value, as in an RFC 6960 CertID, so the same hash data works as an OCSP request. `serialNumber` is upper-case hex without leading zeroes, following the spec's "FFF" example. Lookups ignore case. The configured `security.ca` counts as an installed CSMS root: it is listed and can be deleted. The store holds 20 certificates (`CertificateStoreMaxLength` / CertificateEntries). An install beyond that answers Failed; a certificate that is not a valid, self-signed CA certificate answers Rejected. DeleteCertificate answers Failed for the station's own certificate (M04) and for the last CSMS root while profile 2 or 3 is active, since the station could not reconnect without it. CertificateSigned is checked on the station's clock: the chain must reach an installed CSMS root (V2G root for a V2G certificate), and the leaf must carry the public key of a pending CSR. Every SignCertificate generates a new key pair. A rejected certificate leaves the pending key in place, so a corrected chain can still follow. Firmware updates (1.6 SignedUpdateFirmware, 2.x UpdateFirmware) check the signing certificate against the manufacturer roots and then report the statuses without downloading anything; the firmware signature itself is not checked.

## 2026-10-30 A quirk runs where `use quirk` stands; `--quirk` runs before the station's own statements

`use quirk "q"` executes q's statements at that point, like `call` executes a proc. No separate merge step exists, so the order of statements is the whole rule. Configuration is last-writer-wins: a station statement after `use quirk` overrides the quirk, one before it is overridden. `chaos` rules and `on` handlers accumulate in the order they run, and the engines' existing first-match rules decide between them. Configuration from a quirk used after `boot` fails the station exactly as if written there. `wattsim run --quirk` (and `RunOptions.quirks` / `quirkFiles`) applies quirks as if `use quirk` were the first statements of every station block, so a scenario can still override a profile it is run with. Prepending was the only consistent choice: configuration must come before the station exists, and appending after `boot` would fail every station. A `.ws` value of `--quirk` loads a file; with no names given, every quirk the file declares applies, otherwise only the named ones. Quirk names are global to a run, and a name declared in two files is an error rather than a shadow, so `use quirk "x"` always means one block. A quirk block refuses statements that act (`boot`, `wait`, `expect`, `net`, ...) and `version`. A profile then describes behaviour that combines with any session and any protocol version. A quirk file holds only `import` and `quirk` declarations for the same reason. Files are resolved before anything connects, and `driveVirtual` waits for that, so file reads and plugin imports never move the virtual clock.

## 2026-10-30 Quirk plugins are trusted local code

`use plugin "./x.ts"` imports a TypeScript or JavaScript module with Bun's `import()` and calls its default export with the live `Station`. Nothing sandboxes it. A plugin runs with the permissions of the `wattsim` process, like the `.ws` file that names it, and the user chose to run both. Sandboxing would not change that: a scenario can already point stations at any URL and read any import path, and a plugin that cannot touch the `Station` cannot express a code-level quirk. Mitigations: plugins load only from paths written in a scenario or quirk file the user runs, resolved relative to that file. `wattsim check` verifies that the file exists but never imports it. Nothing loads a plugin from a trace, a URL or the network, and `quirk derive` never writes `use plugin`. Treat a contributed plugin like any other code in a pull request.

## 2026-10-30 `quirk derive` maps findings to statements only where the statement reproduces the trace

`wattsim quirk derive` replays a trace through `@wattsim/csms`'s checker functions (`checkStationCall`, `recordStationCall`, `applyCsmsReply`, `applyCsmsCall`, `checkStationReply`, `applyStationReply`, `expireCsmsCall` after 30 s) per identity. Every finding is listed as a comment with its spec reference and trace line. A statement is written only when running it would make wattsim send what the trace shows. CSMS CALLs of one action that the station always answered with the same CALLERROR, or the same schema-invalid payload, become `on ACTION always`; when only the first k answers were odd, k one-shot handlers. A pattern that skips CALLs is a TODO, because `on` cannot select the k-th CALL. Unanswered CSMS CALLs become `chaos noResponse in`, and a CALL resent with the same id and text becomes `chaos duplicate out`, with an `nth` / `every N from M` trigger only when one selects exactly the observed positions. Missing meter samples are found from the sample timestamps (not the send times, which a lost request's 30 s timeout delays) and the most common gap, then mapped to `chaos drop out MeterValues` the same way. The last lost sample of a recording is invisible, so a draft from a short trace can say `nth 3` where the charger drops every third. The clock offset is the median of station timestamps minus trace time, from messages stamped when sent (StatusNotification) rather than queueable ones. Drift is a least-squares fit, reported over a 30 min span from 50 ppm up. The heartbeat is the median gap. These are heuristics for a draft that a person edits, and the header comment says so. Findings with no statement (`boot.not-accepted`, `tx.seqno`, `meter.backwards`, ...) become `// TODO` lines. The draft goes through the scenario parser and formatter, so it is canonical, and the command checks that it links before writing it.

## 2026-10-30 The CSMS answers a retransmitted CALL from memory

OCPP-J delivers transaction messages at least once. When a connection drops after the CSMS answered, the station sends the same CALL again on the next connection with the same message id, and core's `Connection.requeueInflight` does exactly that. The checker used to treat the copy as a new message: a 1.6 StopTransaction became `tx.unknown-stop`, a StartTransaction became `tx.started-twice` and got a second transactionId (which left the first transaction open for good), and a 2.x Updated or Ended became `tx.seqno` or `tx.after-ended`. Each station's `SessionState.answered` now keeps its last 50 answered CALLs: message id to action, canonical payload (JSON with sorted object keys) and the reply sent, CALLERRORs included. A CALL on a later connection that matches one exactly is a retransmission. The CSMS sends the original reply again, with the same transactionId, records no finding, does not run the responder and leaves the state alone. The `call` event still fires. A CALL that reuses a remembered id with a different action or payload on a later connection is a new CALL, flagged `rpc.message-id-reuse` as a warning. OCPP-J only requires ids to be unique per connection, so this is not a SHALL violation, but such a CALL cannot be told apart from a retransmission. A repeat on the same connection is an error as before and is processed again. BootNotification and Heartbeat are never answered from memory, because their replies carry the CSMS's current time. A station whose ids restart at 1 after a reboot would otherwise get an old BootNotification reply and set its clock back. Processing them again changes no transaction state. The checker functions are `findRetransmission`, `recordRetransmission` and `startConnection`, which numbers connections. A caller that never starts a connection, such as `quirk derive`, stays on connection 0 and sees no retransmissions.

## 2026-10-30 Offline backlog, whole-Wh meter readings and memory bounds in the CSMS

`time.skew` excuses past timestamps on every CALL received in the first `offlineDrainMs` (60 s, on the CSMS clock) after a reconnect, not on the first connection. Core queues every CALL while offline, and a queued StatusNotification carries the time of the status change, so 10 min offline gives a 10 min old timestamp. This is the simplest heuristic that needs no knowledge of the station's queue. Its cost is that a station whose clock is behind goes unflagged for its first minute after each reconnect, and is flagged on its next non-queueable message after that. Timestamps ahead of the CSMS clock are always flagged. A drain that takes longer than 60 s, such as a large backlog on a slow link, can still produce warnings.

`meter.backwards` allows a drop of less than 1 Wh when either value is a whole number of Wh: 1.6 meterStart and meterStop are integers, and a whole-Wh value has 1 Wh resolution. A reading of 1234.5 Wh followed by `meterStop: 1234` is truncation, not a decrease. Between two finer readings the tolerance stays at 1e-6 Wh.

`Csms.violations` keeps the newest `maxViolations` (10000). `report()` counts come from running totals, so they stay exact after the list is trimmed. `report().violations` and the JUnit failures list only the retained violations. A session whose station has been disconnected for `forgetAfterMs` (1 h, on the injected clock) is dropped when the next connection opens or closes. If the station comes back after that, it is checked like a new one: a 1.6 station that resumes without a BootNotification gets `boot.not-accepted`, and its queued messages for transactions the CSMS forgot get `tx.*` findings. Its earlier violations stay in the totals. `forgetAfterMs: Infinity` keeps every session.

## 2026-10-30 Replay sends what reached the CSMS; `toScenario` output sends exactly the trace's station CALLs

This entry supersedes parts of the three trace entries above.

Replay now sends each station frame as it reached the CSMS when the trace was made, not as the station sent it. The proxy decides a chaos outcome when the frame arrives, before it records the entry, and notes it in `meta.wattsim.chaos`: `delivered` holds the text it passed on when a rule changed it (corrupt, wrongId, callError on a CALLRESULT, mutate), and `copies` holds the count for a duplicate. Replay skips a dropped frame (drop, noResponse, callError on a CALL). It sends `delivered` when present, `copies` times, and delays it by `delayMs` when pacing. A changed frame from an older trace without `delivered` is skipped and reported in `ReplayReport.notes`, which do not fail the run. The CALLERROR the proxy sends the CSMS for a CSMS CALL reached the CSMS, so replay sends it, re-addressed. The one it sends the station never came from the CSMS and is not expected. A wrongId frame keeps its random id. The CSMS's answer to that id is an orphan in the trace and shows up as unexpected. Fixing that would need correlation against delivered ids, and nothing has needed it yet.

After the last entry replay keeps the socket open for `settleMs` (default 1000 ms, `--settle <s>`) and reports CSMS frames that arrive meanwhile. Before this change, a CSMS that sent one extra CALL after the last expected frame passed.

Ignore keys are now key paths matched against the end of a key's path, with array positions left out. A leading `$.` anchors a path at the payload root. The defaults are `transactionId`, `requestId`, `remoteStartId`, `reservationId`, `chargingProfileId`, `$.id` (ReserveNow, ClearDisplayMessage, GetDisplayMessages, ClearVariableMonitoring), `chargingProfile.id`, `chargingSchedule.id` and `message.id`. The bare `id` the defaults used to contain also removed `evse.id`, so a CSMS that triggered the wrong EVSE matched. `evse.id`, `connectorId` and `evseId` are now always compared.

`toScenario` output is now required to send the trace's station CALLs, in order, and nothing else. The test runs every vendored fixture against FakeCsms and compares the CALL sequences. `boot` has two side effects a trace may not show: StatusNotification for EVSE 1..N once Accepted, and its own retry after Pending or Rejected. A BootNotification becomes `boot` only when the CSMS accepted it and the next station CALLs are exactly those N StatusNotifications. N is the length of that run after the first such boot, because `evses` is one value per station. Every other BootNotification becomes `send BootNotification {payload}`, which has neither side effect. The 1.6 fixtures send connector 0 first, so they all take the `send` form. A trace that opens with a CSMS CALL gets `connect` before its `expect call`.

The reader accepts exactly what the vendored schema's `format: date-time` accepts under Ajv and ajv-formats, because the schema is the authority. That covers `t` or whitespace as the separator, lower-case `z`, `+HH`, `+HHMM` and `+HH:MM` offsets, and a leap second only at 23:59 UTC. `parseDateTime` repeats Ajv's checks rather than relying on `Date.parse`, which rejects several of these forms. A leap second reads as the first instant of the next minute, so it sorts after the second before it.

`Correlator` forgets a CALL once it is answered and keeps at most 1000 unanswered ones (`MAX_PENDING_CALLS`), dropping the oldest. The proxy and the trace writer run for as long as a session lasts. A late answer to an evicted CALL no longer correlates: its Open OCPP Trace record loses `action`, and the proxy's chaos rules see it without one. `correlate()` over a trace already in memory keeps everything.

## 2026-10-30 Server mode: SQLite through Drizzle, CodeMirror in the browser, runs in process

Server mode persists run history, saved scenarios, recordings and CSMS conformance reports with `bun:sqlite` and Drizzle (DESIGN.md §5): `drizzle-orm` 0.45.4 at runtime in `@wattsim/server`, `drizzle-kit` 0.31.11 as a dev dependency that generates the SQL migrations committed under `packages/server/drizzle`. The server applies them on every start. Drizzle gives typed queries and reviewable SQL migrations without a native driver, since `bun:sqlite` ships with Bun. `wattsim ui` stores `<--data>/wattsim.db`, default `~/.wattsim`. `startServer()` without `dataDir` uses the same schema in an in-memory database, so the library API, its tests and the MCP server write nothing to disk and run one code path. Rows hold JSON columns for run results, events and reports; history lists are capped at 200 rows per request. A run still marked `running` when the server starts is set to `error`.

The browser editor is CodeMirror 6 (`@codemirror/state`, `view`, `language`, `lint`, `commands`, `autocomplete` and `@lezer/highlight`, exact versions in `packages/ui/package.json`), in a lazily loaded chunk of the Scenarios page. Its language is a `StreamLanguage` whose keyword list is the scenario lexer's `KEYWORDS`, imported from `packages/scenario/src/lexer.ts` by relative path: the file has no imports, so nothing else of the scenario package reaches the bundle, and grammar additions show up without a generated file. Diagnostics come from `POST /api/scenario/check` (parse plus link, the same steps as `wattsim check`), 400 ms after the last keystroke. A Lezer grammar would give a real tree, but the checker is the authority on errors and a second grammar would drift.

Runs from the UI execute in the server process through `@wattsim/scenario`'s `run`, on a `VirtualClock` driven by `driveVirtual` or on the wall clock with a speed factor, and are cancelled through the run's `AbortSignal`. A browser scenario may not `use plugin`: that would import and execute a module from the server's disk for anyone who can reach the UI, which matters once the Docker image binds 0.0.0.0. Quirk `import` paths resolve against the data directory.

Stream volume: `run`, `csms` and `csms.session` messages are coalesced to one per key per 250 ms, `run.event` is capped at 200 per run (frames are never streamed; they go to the run's trace), and `csms.violation` at 50 per second, after which the UI refetches the list while it is behind the totals. There is no `csms.frame` message: the CSMS-side frames of a station are kept in a 500-frame ring per identity and fetched by the page that shows them.

## 2026-10-30 The milestone-4 faults are separate types beside the original chaos effects

The new chaos faults (`jitter`, `reorder`, `halfOpen`, `slowRead`, `reconnectStorm`, `invalidEnum`, `missingField`, `timestamp`, `oversized`) are core's `ChaosFaultEffect` and the scenario AST's `ChaosFaultStmt` (kind `chaosFault`). `ChaosEffect`, `ChaosFault` and `ChaosStmt` did not change. The trace proxy switches over `ChaosEffect` exhaustively and `parseChaosRules` builds `{ kind: stmt.fault }` as a `ChaosEffect`, so adding members to either union would have broken `@wattsim/trace`. `ChaosRule.effect` now accepts both unions. `ChaosEngine.decide` resolves `jitter` and `slowRead` to a plain delay, so an older consumer sees a `delay`. It reports the other new faults in `ChaosDecision.fault` with `effect: null`, which an older consumer treats as no chaos. The proxy cannot apply the new faults yet. `--chaos "jitter 1s..2s"` fails there with "is not a chaos rule".

`delay`, `jitter` and `slowRead` share the delay slot, so the existing composition rule covers them: one delay and one other fault per frame, whatever the declaration order. `jitter` draws from the engine's seeded RNG after the rule matches, so it is reproducible per `--seed`. `slowRead` counts per rule: the n-th frame it delays waits n steps. Protocol faults never match an inbound frame and `slowRead` never matches an outbound one, even in a rule without a direction, so such a rule spends no `once` and draws no `probability` on those frames.

## 2026-10-30 Chaos state belongs to the socket

A frame held by a delay, `jitter`, `slowRead` or `reorder`, and a `halfOpen` in force, are discarded when their socket closes. This includes frames the original `delay` rule holds. Before, a delayed frame was delivered when its timer fired even if the socket had closed meanwhile. Then an inbound reply could settle the requeued copy of its CALL on the new connection, and an outbound one went out on the new socket next to the station's own retransmission. Discarding is what a real connection does with bytes in flight, and it means `disconnect()` (which `net drop` and the end of a run call) leaves no chaos timers behind. `disconnect()` also cancels a `reconnectStorm`.

`reorder` counts frames that are delivered: written to the socket for `out`, dispatched for `in`. Because one CALL is in flight at a time, a held outbound CALL is released only by the next CALLRESULTs the station sends or, once it times out, by the next CALL. `halfOpen` swallows writes and ignores reads from the frame that triggers it, frame included. With `for d`, the station closes the socket after `d` and reconnects with its normal backoff. Bun's client WebSocket still answers protocol-level pings, so a CSMS that relies on ping timeouts still sees the socket as alive. A `reconnectStorm` drops the socket every `T/K`, starting one interval after the trigger. A storm that started at the trigger would requeue the triggering CALL and resend it on the first reconnect, and without `once` that resent CALL would start the next storm. A dropped socket is detached and treated as closed at once (close code 1001), and the next socket opens without backoff.

## 2026-10-30 Protocol faults read the generated Zod schemas and break them on purpose

`invalidEnum`, `missingField`, `timestamp` and `oversized` mutate a copy of an outbound payload after strict validation (`request()` validates when the CALL is queued; a reply is validated before it is sent). The frame goes out mutated and is reported through the `chaos` event, never as a `violation`. Finding the field to break needs the schema: `faults.ts` walks the generated Zod v4 schemas through `_zod.def` (object `shape`, `optional.innerType`, `array.element`, `enum.entries`, string `checks` with format `datetime`). A CALLRESULT uses the action's response schema. `invalidEnum` without a path changes the first enum field in payload key order, depth first, to `wattsim-invalid-enum`, which no OCPP enum contains. `missingField` without a path deletes the first required top-level field present. `timestamp` shifts every `date-time` field. `oversized N kB` adds a `wattsimPadding` string so the payload's JSON is N × 1024 bytes. Every OCPP object schema is closed, so the extra key is also a schema break, and padding an existing field would have meant choosing one per action. A payload with nothing to break goes out unchanged. As the oracle, `@wattsim/csms` flags `invalidEnum`, `missingField` and `oversized` as `schema.request` and `timestamp` beyond its 5 min tolerance as `time.skew`. In 2.x, a TransactionEvent that fails the schema leaves a `tx.seqno` gap behind it.

## 2026-10-30 Behavioural faults: what each statement does on the wire

`reset hard` is a power loss: it drops the socket, reconnects and boots with 2.x reason `PowerUp`, then ends the lost transactions with reason `PowerLoss` (1.6 and 2.x both have it). Their stop messages queue behind the BootNotification, as 1.6 §5.14 describes for a hard reset. `reset soft` is a software restart: transactions end first with reason `Reboot` ("a locally initiated reset/reboot", both versions), then the station reconnects and boots with 2.x reason `ApplicationReset`. The CSMS-requested resets keep `HardReset` / `SoftReset` / `ImmediateReset`. These statements model a station that resets on its own. `bootLoop N` reboots after the whole boot sequence, the StatusNotifications included. To reboot before them, the station would have to drop CALLs that are already queued, and its public API has no way to do that. Reboots after the first give 2.x reason `Watchdog`. `fault evse N [code]` uses `setStatus` (1.6 `errorCode`, default `OtherError`, validated against ChargePointErrorCode). In 2.x it adds a NotifyEvent for component `Connector` and variable `AvailabilityState`, with `actualValue` `Faulted`, `trigger` `Delta`, `HardWiredNotification`, the code as `techCode`, and an `eventId` that is unique per station. The statement does not stop a running transaction, which leaves room for a scenario that keeps one going on a faulted connector. `meter backwards` clamps the register at 0. `net drop d duplicate` adds a chaos `duplicate` rule for outbound CALLs (`ChaosMatch.messageType`) at reconnect. The rule is removed once as many distinct message ids have gone out as `pendingRequests` counted then. The CSMS flags the second copy as `rpc.message-id-reuse`.

## 2026-10-30 `ev plug` properties come from a table checked against `EvConfig`

Every non-function `EvConfig` field is an `ev plug` property, under its name and under its name without the unit suffix (`cableMaxA`, `cableMax`). `soc` and `target` are kept as aliases. `EV_CONFIG_FIELDS` in `packages/scenario/src/ev-props.ts` maps each field to its unit and uses `satisfies Record<EvConfigField, EvPropUnit>`, so a field core adds or removes fails the scenario typecheck at that table. TypeScript types do not exist at run time, and `new EvModel().config` lists only the fields that have defaults. A table the compiler keeps complete was therefore the only way to make an unknown property an error that names the valid ones. Values convert to the field's unit (`Wh` to kWh, durations to ms, `%` to a fraction, `°C`). `true` and `false` are booleans unless a variable has that name. An unknown property, or a unit that does not fit, now fails the station. Before, it was silently ignored. The lexer reads `°C` as a unit word, and property numbers may carry a sign.

## 2026-10-30 Station power is the minimum of every limit, evaluated at the phases in use

`resolvePower` (packages/core/src/phases.ts) decides an EVSE's phases and offer whenever an EV is plugged in or unplugged, or a limit changes. Phases in use are min(station `phases`, EV `phases`, `numberPhases` of the schedule period that sets the binding limit). The offer is min(EVSE `maxCurrentA`, EV `cableMaxA`) × phases × V, capped by the smart-charging limit. The EV then takes min(offer, its own `maxCurrentA` × curve(soc) × temperature derate × phases × V). A limit written in A is a per-phase current and is rescaled to the phases in use, so 16 A stays 16 A per phase after a switch to one phase. A limit in W is taken as is. `ProfileStore.limitDetail` exposes the per-phase amps and phases for this, and the composite schedule is unchanged. The meter derives current from the phases in use, so a 1-phase EV on a 3-phase EVSE now reports its real per-phase current (16 A, not 5.3 A) at the same power. `numberOfPhasesUsed` appears on 2.x TransactionEvents only when the phases in use differ from the wiring, and `cableMaxCurrent` only for an EV with `cableMaxA`, so a plain session's payloads are unchanged.

## 2026-10-30 Battery temperature: a closed-form first-order model

The pack temperature follows dT/dt = h (P/B)² − c (T − ambient): heating with the square of the C-rate (I²R losses), Newton cooling towards `ambientC`. Defaults: `heatPerHourC` 6 °C/h at 1C, `coolingPerHour` 0.5/h. `EvModel.tick` integrates it exactly for the power of the step, so the result does not depend on the meter interval. AC charging (0.2-0.4C) warms a pack by under 2 °C, and a 2C session heats it towards derating within half an hour. Defaults are chosen so that existing sessions at 20 °C behave exactly as before. The default derating curve is linear between 20% at -20 °C, 50% at 0 °C, 100% from 15 to 40 °C, 50% at 50 °C and 0 from 60 °C; `temperatureDerate` replaces it. Temperature is clamped to -40..90 °C. Power is re-evaluated at each integration step (meter tick, status or limit change), like the soc curve.

## 2026-10-30 V2X discharge: 2.1 only, for a `v2x` EV, from setpoints and negative limits

On a 2.1 station with a `v2x` EV, a schedule period's negative `setpoint` is a discharge command. A negative `limit` without a setpoint, the pre-2.1 convention the schema still mentions, is one too. The discharge rate is bounded by the tightest `dischargeLimit` (TxProfile/TxDefaultProfile and the Max / ExternalConstraints caps; a station-level one is shared like a station-level limit), the EVSE rating, the cable and `maxDischargeCurrentA`. The EV stops at `minDischargeSoc`. A positive setpoint is a charging target below the offer. Setpoints come only from the profile that sets the transaction limit, because caps limit and do not command. Values in A are per phase, like `limit`. A unidirectional EV, and every 1.6 and 2.0.1 station, treats a negative limit as zero (SuspendedEVSE), as before. While discharging the status stays Charging, because 2.1 has no discharging charging state. Power.Active.Import and Current.Import go negative (signed values, as the 2.1 conditions' sign convention uses), Power.Active.Export carries the magnitude, and the meter fills a separate Energy.Active.Export.Register, so the import register stays monotonic for CSMS checks. A Full V2X EV wakes up to discharge and charges back to `targetSoc` afterwards. `setpointReactive`, per-phase `_L2/_L3` values, `v2xFreqWattCurve` / `v2xSignalWattCurve`, Dynamic profiles and the 2.1-only purposes are not modelled; SetChargingProfile still rejects the latter two.

## 2026-10-30 OCMF signed readings: fields, signature input and synchronous signing

`signedMeterValues` makes every energy register reading an OCMF record: `OCMF|{payload}|{"SA":"ECDSA-secp256r1-SHA256","SD":"<hex DER>"}`. The signature is ECDSA P-256 / SHA-256 over the UTF-8 bytes of the payload JSON exactly as it appears between the pipes. The key is per station: generated on first use, or `meterSigningKey` (PKCS#8 PEM, P-256 only). The payload fills `FV` ("1.0"), `GI` (vendor + model), `GS` (serial, else the identity), `GV` (firmware, when set), `PG` (`T<n>` per meter inside transactions, `F<n>` outside, counting from 1), `MV`, `MM`, `MS` (`<serial or id>-<evse>`), `IS`, `IT` (OCPP idToken type mapped to OCMF table 17; NONE without one), `ID`, `IF` (`ISO15118_PNC` for eMAID only), and one `RD` reading with `TM` (UTC, `,mmm+0000 S`), `TX` (B, C, E; omitted outside a transaction), `RV` (kWh, the plain reading's whole Wh / 1000 so both agree), `RI` (`01-00:01.08.00`), `RU` (kWh), `RT` (AC), `EF` (empty) and `ST` (G). Left out: `IL` (no identification level is modelled), `TT`, `CF`, `LC` (no cable loss compensation), `CT`/`CI`, `CL`, and `SE`/`SM` (their defaults, hex and DER, apply). Errors, time sync loss and tariff-change readings (`TX` X, T) are not produced. 2.x puts the record base64-encoded in the register's `signedMeterValue` with `signingMethod`, `encodingMethod: OCMF` and the base64 SubjectPublicKeyInfo as `publicKey` (2.0.1 requires both). 1.6 adds a second Energy.Active.Import.Register sampled value with `format: SignedData` whose value is the record, because a 1.6 value cannot carry both.

Signing uses node:crypto (`sign`, DER encoding) synchronously instead of WebCrypto. A reading is sampled, put into a payload and handed to the connection in one synchronous step. WebCrypto's `sign` is asynchronous, so a later reading (another trigger at the same instant) could overtake an earlier one, and 2.x `seqNo` order would no longer match send order. The test suite verifies every record independently with WebCrypto (`crypto.subtle.verify` over the payload bytes). Stations without the option never create a key or a signer.

## 2026-10-30 Tariffs: local time, element selection and what costDetails reports

2.1 TariffType has no time zone, yet its times of day are local ("as shown to the EV driver"). wattsim takes the station's IANA time zone: `StationConfig.timeZone`, default UTC, settable through the 2.x device-model variable `ClockCtrlr.TimeZone`. Local times come from `Intl.DateTimeFormat`. A local boundary maps to the first instant the wall clock reaches it, and a time skipped in spring maps to the instant of the jump. Within each dimension (energy, charging time, idle time) the first price element whose conditions all hold applies. Conditions are evaluated at every instant where one can flip: local time-of-day boundaries, midnight for weekday and date conditions, energy thresholds and duration thresholds. These cuts are computed in closed form within a step at constant power, so cost does not depend on the meter interval. Elements with a negative power, current or energy bound price discharging (the 2.1 sign convention). All other elements price charging only, so a plain retail price never pays out for V2X energy. A discharged kWh at a positive discharge price is a negative cost. The fixed fee is the first fixed element that matches at the transaction start. Payment-brand conditions cannot be evaluated, so SetDefaultTariff answers ConditionNotSupported for them. Tax rates stack per `stack` level. `minCost` / `maxCost` bound the running total as well as the final one. Reservation prices are ignored because reservations are not modelled.

`costDetails` goes on every 2.1 TransactionEvent of a transaction with a tariff, with `transactionInfo.tariffId`. `totalUsage.energy` is net Wh (import − export). `totalUsage.chargingTime` is the whole session duration and `idleTime` the time without energy transfer, as the schema's descriptions define them. Charging periods start whenever the applicable price elements, the charging/idle state or the tariff change. Their Energy volume is net Wh and ChargingTime / IdleTIme (the schema's spelling) are seconds. A transaction takes the default tariff in force at its start: the EVSE's own, else the station's. One default tariff exists per EVSE and `validFrom`. A tariffId names one tariff, so the same id with other content anywhere is DuplicateTariffId, and the same content on another EVSE is accepted. ChangeTransactionTariff keeps the cost so far, charges no new fixed fee, refuses another currency (NoCurrencyChange) and sends a `TariffChanged` TransactionEvent. GetTariffs lists the changed tariff as a DriverTariff. ClearTariffs removes default tariffs only. A tariff has at most 100 price elements (TooManyElements). 2.0.1 has no tariff messages; the station stores the CSMS's running cost from CostUpdated and TransactionEventResponse `totalCost` as `tx.csmsTotalCost`. California Pricing (2.0.1 display messages and device-model variables) is not modelled.

## 2026-10-30 Plug & Charge uses the station's V2G chain; the responder URL is a placeholder

`Station.plugAndCharge` sends Authorize with idToken type eMAID (the EV's `emaid`) and `iso15118CertificateHashData` for the V2G certificate chain installed through SignCertificate / CertificateSigned, leaf first, at most four. The hash data comes from `StationSecurity.list(['V2GCertificateChain'])`, the same code GetInstalledCertificateIds uses. A real EV would present its own contract certificate. wattsim has no ISO 15118 stack and no contract certificate store, so the installed chain stands in for it. That still lets a CSMS exercise its certificate status path. `responderURL` is required but wattsim does not read the AIA extension, so it is `http://ocsp.wattsim.test/` (`PNC_OCSP_RESPONDER`). Without an installed chain, Authorize carries the eMAID alone. The transaction starts only when `idTokenInfo.status` is Accepted and `certificateStatus` is absent or Accepted. An `iso15118` EV sends NotifyEVChargingNeeds after its transaction is accepted. On 2.1, a V2X EV asks for `AC_BPT` with its charge and discharge power and its V2X energy window.

## 2026-10-30 The proxy applies the milestone-4 faults as a station would; chaos engines live per charger

`wattsim proxy --chaos` accepts every DSL chaos fault. Each connection applies core's `ChaosEngine` decisions the way `Connection` does, with the proxy in the station's place. It reuses `decide` (so `jitter` and `slowRead` arrive as a delay drawn by the engine) and `mutatePayload` for the protocol faults. `out` is charger to CSMS, so the protocol faults change only what the charger sends. `reorder` counts frames the proxy actually passed on in the same direction, duplicates and the CALLERROR it sends back included, as `Connection` counts frames written or dispatched. `halfOpen` passes nothing either way from the frame that triggers it, frame included. Charger frames still go through the rules while half-open, because a station's writes are still decided before the dead socket swallows them. CSMS frames are not looked at, because a half-open station stops reading. A proxy cannot make a socket half-open for the charger, and it cannot make the charger reconnect. So for `halfOpen for d` and `reconnectStorm`, dropping the connection means closing the charger's socket and the upstream socket with 1001, and the charger reconnects on its own backoff through a new upstream connection. The `close` event reports these drops with side `proxy`. A storm belongs to the identity, not the connection, so its remaining drops hit the connections the charger opens again. It ends with `stop()`. As in core, what a connection holds (delayed and reordered frames, the half-open state and its timer) is discarded when either side closes, so no timers outlive it.

This replaces "chaos counters are per connection on the CLI": the CLI now keeps one engine per identity for the proxy's lifetime (`chaosPerIdentity`). A station keeps its engine across reconnects, and with an engine per connection `halfOpen for 5s out Heartbeat nth 1` would fire on every connection, so the charger would never get through. Counters, `once` and `slowRead` steps now carry over a charger's reconnects. A library caller that passes its own `chaos` function still decides this for itself.

Recording follows the existing rule: the frame as its sender sent it, and the outcome in `meta.wattsim.chaos`. A `jitter` or `slowRead` is noted under its own name with `delayMs`, a `reorder` with `after`, and a protocol fault with the mutated text in `delivered`. Every frame a half-open connection swallowed is noted `halfOpen`. Replay skips `halfOpen` station frames, sends delayed ones `delayMs` later and holds a `reorder` frame until `after` later station frames have been sent. A reordered frame still held when the trace ends never reached the CSMS, so replay skips it with a note. Replay uses one connection per identity, so it does not reproduce the drops. A frame held when its connection closed, but released by frames on the next one, is sent anyway, because the trace has no connection boundaries.

## 2026-10-30 Scale is measured against a CSMS in another process; the perf test is opt-in

`scripts/perf.ts` runs N real `Station`s with real WebSockets in one process and `@wattsim/csms` in a child process, so RSS, heap, event-loop lag and heartbeat jitter are the simulator's alone. Each README row runs in a fresh process, so RSS starts clean. Lag is the overshoot of a 10 ms interval timer. Jitter is |actual − nominal| between a station's consecutive Heartbeat CALLs, taken when the frame leaves the socket. `--via scenario` measures the same fleet through the interpreter, as `wattsim run` drives it. `packages/core/test/perf.test.ts` asserts the 10k budget (under 1 GB RSS, lag p99 under 50 ms, jitter under 1 s) and runs only with `WATTSIM_PERF=1`. One run takes several minutes and needs 10k free file descriptors and ephemeral ports, which a shared CI runner does not promise.

Strict validation stays on everywhere, and validators are not cached per payload. The Zod schemas are compiled once per action at import. Profiles of 10k stations put validation at about 2 % of CPU in a virtual run and below the noise in a wall-clock run, so it was not a hot spot.

## 2026-10-30 VirtualClock keeps its timers in a binary heap and cancels lazily

A fleet on one virtual clock arms and cancels a request timeout for every CALL. A sorted array with `indexOf` + `splice` made each cancel O(timers), and at 10k stations that was 36 % of the CPU of a virtual run. Timers now live in a binary min-heap on (due, scheduling order), so firing order is unchanged. `cancel()` marks the timer; marked timers are dropped when they reach the top, or all at once when they outnumber the live ones (above 64). `pendingTimers()` counts live timers only. A one-shot timer that fired is marked too, so cancelling it afterwards is a no-op.

## 2026-10-30 Fleet selection: `--shard` by position, `--ids` by loop variable

`wattsim run --shard i/n` keeps the stations whose position in the expanded fleet (0-based, file order, every block) modulo n is i. `--ids a..b` keeps the template stations whose loop variable is in a..b. A station block without `for` has no id, so `--ids` drops it; with `--shard` it is distributed like any other station. Both flags together keep what both select. Selection runs after the whole fleet is expanded and checked for duplicate names, and before any station is created. So every process reports the same scenario errors and keeps a disjoint part of the same fleet, with no coordinator (DESIGN §3). Random draws are keyed by station name and seed, never by position, so a station draws the same `choose` branch and durations whichever process runs it. Barriers count the stations of their own process only, because a barrier across processes would need a coordinator. A shard that selects nothing finishes at once with exit 0, so a fixed process count works for any fleet size. `--metrics-port-base B` serves `/metrics` on B + the shard index (B without `--shard`), and it excludes `--metrics`.

## 2026-10-30 `--connect-rate` paces connections on the run clock and is off by default

`ConnectPacer` hands out at most R connection slots per second in call order, and `pace(station, pacer)` makes a station's `connect()` wait for one. Station-initiated reconnects after a drop are not paced; they keep their own backoff. The CLI paces on the run's clock, so in a `--virtual` run station k connects k / R virtual seconds in and the run stays deterministic. The default stays unpaced, so existing runs behave as before. Unpaced, 10k stations still connected to a local CSMS in 0.6 s with no refusals, but the event loop stalled for 250 ms (lag p99). At 1000/s the fleet connects in 10 s with lag p99 around 2 ms.

## 2026-10-30 Stations that cannot run `expect` keep no frames

The interpreter's frame log exists for `expect` cursors. A station whose body, nested blocks and procs contain no `expect` (quirks cannot hold one) now gets a log that advances its sequence numbers but stores nothing, so cursor arithmetic is unchanged and memory stays flat. Measured with `scripts/perf.ts` on 2000 scenario-driven stations over 6 virtual hours: 205.7 KB of heap per station before, 17.1 KB after, same speed. A station that can assert still keeps its 2048-frame window.

## 2026-10-30 The CSMS checker warns once about a station that booted before it, and orders meter readings by sample time

Two false positives found against real EVerest (interop/README.md, "Findings against real EVerest").

**Boot before this CSMS.** A BootNotification belongs to the station's start-up, not to each connection: 1.6 §4.2 has the charge point send it "after start-up", and 2.0.1 B01 (Cold Boot Charging Station) starts with the station powering up. 2.0.1 B04 (Offline Behavior Idle Charging Station) says what a station does when it reconnects instead: it sends StatusNotificationRequest for all its connectors after an offline period longer than `OfflineThreshold` (B04.FR.01) and for the changed ones otherwise (B04.FR.02), with no BootNotification. So when the CSMS process restarts under a running station, the station is right not to boot again, and the new CSMS never sees a boot. The checker used to flag every message of such a station as a `boot.not-accepted` error. Now, when a session has never seen a BootNotification and the station's first request is one a booted station starts with (StatusNotification, Heartbeat, MeterValues, StartTransaction, StopTransaction, TransactionEvent), that first request gets one `boot.not-accepted` warning, "first message from <id> is not a BootNotification: the station may have booted against an earlier CSMS". Later requests in the session get nothing more, reconnects included. The warning cites `1.6 §4.2 Boot Notification` or `2.0.1 B01 / B04` (2.1: `2.1 B01 / B04`). It is still an error per request when the first request is something else (an Authorize, a DataTransfer), when a BootNotification arrived in this session and was not accepted yet (unanswered, a CALLERROR, or still Pending or Rejected), or after a later Rejected or 2.x Pending boot. A CSMS cannot tell a station that booted elsewhere from one that skipped its boot and opens with a StatusNotification; the warning keeps the case visible without failing the run. All versions are treated the same, because B04 describes the same reconnect for 2.x. The B04 requirement ids are as libocpp cites them in `charge_point.cpp`; the PDF text was not at hand. `SessionState` has two new fields for this, `bootSeen` and `firstCall`. A station whose session `forgetAfterMs` dropped now gets this warning, not an error per message as the entry on memory bounds says.

**Meter readings by sample time.** A 2.0.1 Ended event carries the `TxEndedMeasurands` samples "every SampledDataTxEndedInterval seconds from the start of the transaction" (SampledDataCtrlr / AlignedDataCtrlr, used by J02), and a 1.6 StopTransaction's `transactionData` repeats samples too. Comparing readings in arrival order against the last one flagged the Ended event's `Transaction.Begin` 0 Wh after an earlier `Updated` with 23 Wh. `meter.backwards` now compares register readings by `meterValue[].timestamp` (1.6 meterStart and meterStop by the StartTransaction / StopTransaction timestamp), per transaction, measurand register, phase and location. A reading is backwards when it is below a reading sampled at or before it, or when it is a late sample above a reading sampled after it. Readings with equal timestamps count in arrival order, so 1.6 readings stamped in whole seconds still compare as before. The 1-Wh truncation tolerance is unchanged. Each running transaction keeps its readings sorted by time, an identical repeat stored once, at most 500 per register (the oldest go first), and drops them when it ends, since nothing is compared against an ended transaction. A maximum and the latest timestamp would not do: a late sample has to be compared with the readings on both sides of it. 1.6 `transactionData` is now checked at all; before, only meterStop was. A reading without a parsable timestamp counts as the newest.

## 2026-10-30 Server mode limits what a reachable UI can make the server do

No auth stays (DESIGN.md §3), but a security review showed three ways a request could do more than the person at the UI meant: an 88-byte scenario (`station "s{i}" for i in 1..2000000`) blocked the process for 7 s and took 12 GB while the interpreter expanded the fleet; `import "/etc/passwd"` read any file and echoed its path and first token in the diagnostic; and any web page could POST to the API, because every body was read as JSON whatever its content type.

**Fleet size.** `link` and `run` take `maxStations`. `link` counts the fleet from the station blocks and range bounds (literals, or `let`s that hold integers), summed over blocks, without allocating, so `/api/scenario/check` stays parse plus link. `run` counts again from the resolved bounds before it builds any instance, so a scenario that reaches the run some other way is capped too. A fleet over the cap is a `ParseError` at the range start of the block that passes it: "the fleet has N stations, more than the limit of M". The CLI sets no cap, because the user runs their own files and `--shard` exists for big fleets. The server caps at 10000 (`wattsim ui --max-stations`), the scale one process is measured at. It also runs at most 4 scenario runs at once (`--max-runs`, then 429) and stops a real-time run after 1 h with status `error` (`--max-run-time`, `0` for none). Virtual runs already stop after 24 h of virtual time.

**Imports.** `link` takes `root`: an `import`, `--quirk` file or `use plugin` path outside it is a `ParseError` ("import outside the scenario folder", "use plugin outside the scenario folder") and nothing is read or probed. The check is made on the path as written and again with symlinks resolved; for a path that does not exist, the deepest existing ancestor is resolved, so a symlinked directory cannot point a missing file outside either. The server's root is a new folder, `<data>/scenarios`, created on start, and browser imports resolve against it. Before, they resolved against the data directory itself, which holds `wattsim.db`. Without a data directory (the library, `wattsim mcp`) the root is the working directory. The CLI passes no root.

**Plugins at run time.** The server refused `use plugin` when it checked a scenario, but the run linked the scenario again and loaded its plugins, so a quirk file changed between the check and the run could still load one. `run` now takes `linked`, the result of the check's `link`, and uses it instead of linking again, so the run reads no file. `allowPlugins: false` (on `link` and `run`) refuses any `use plugin` before the plugin file is probed or imported. The server passes both. The CLI keeps linking at run time with plugins allowed.

**Origins.** Every state-changing request (POST, PUT, PATCH, DELETE) and the `/api/stream` upgrade is checked in `onRequest`. When an `Origin` header is present it must be the server's own or in `--allow-origin`, else 403. "Own" means the origin's host:port equals the request's `Host`, so every name the server is reached under works (127.0.0.1, localhost, a LAN name in Docker) without a list. The scheme is not compared, so a TLS-terminating reverse proxy that keeps `Host` also works. A request without `Origin` is not from a web page (curl, the MCP client, tests) and passes. A request with a body must also be `content-type: application/json`, else 415. A page can send that type cross-origin only after a CORS preflight, and the server sends no CORS headers, so the browser stops the request. `curl -d` without `-H 'content-type: application/json'` now gets 415; that is the cost. The stream refusing foreign origins keeps a page from reading the frame log over a WebSocket, which CORS does not cover.

The Vite dev server (`ui-dev`) proxies `/api` with `changeOrigin`, so the browser's `Origin` (the dev server) no longer matches. Its proxy now replaces an `Origin` equal to its own `Host` with the API's origin and passes any other origin through for the API to refuse. Allowing `http://localhost:5173` on the server instead would have let any app on that common port drive it. `--allow-origin` covers other setups.

DNS rebinding: a page on a name that rebinds to 127.0.0.1 sends an `Origin` that matches its own `Host`. When the server listens on a loopback address (the default), every request, reads included, must carry a loopback `Host` (127.0.0.0/8, localhost, [::1]), which refuses rebound names. Bound to 0.0.0.0 (the Docker image) the server cannot know its public names in advance, so that check is off there: anyone exposing it beyond their machine needs a reverse proxy with auth.

## 2026-10-30 Emulated Modbus meters: own server, vendor maps from public documents, a few emulator rules

`@wattsim/modbus` has its own Modbus TCP server and client on `Bun.listen` / `Bun.connect`, written from the Modbus Application Protocol v1.1b3 and Messaging on TCP/IP v1.0b specifications. It covers FC 03, 04, 06 and 16 and has no dependency. The protocol is small, and a library would add a dependency to the simulator's network path without covering the vendor quirks.

The register maps come from the vendors' public documents, cited in each map: the Eastron "SDM630Modbus Smart Meter Modbus Protocol Implementation V1.8" (2019) for the SDM630-Modbus V2, whose own user manual (2016 V1.3) has no register table, and Carlo Gavazzi's "EM24_E1 (Ethernet) Communication Protocol v0 rev 1.2" (2018). The serial EM24 has a different map, and the Ethernet E1 is the one a Modbus TCP controller reads. The behaviour the documents describe is emulated: SDM630 float32 with the most significant register first, at most 80 registers per read, exception 02 for part of a float, and FC 03/04/16 only. For the EM24: INT32 with the least significant word first and value weights, FC 03 equal to FC 04, FC 06 only, the identification code at 000Bh answering only a one-register read, the 5Ah tariff write, and CT/VT read-only as on the AV2 model. Where a document is silent, wattsim decides:

- Inside a documented table, a register that no parameter covers reads 0, as meters do for parameters that do not apply to the wiring. Outside the documented ranges a read is exception 02. Demand, THD, hour counters and tariff meters read 0, because wattsim does not model them.
- The SDM630 phase angle is atan2(Q, P) in degrees. The EM24 PF sign is the reactive sign (lead negative), as its document defines it. In `MeterReading`, the power factor carries the sign of the active power.
- The SDM630 single-register "instrument type specific value" is not emulated, since the document does not give it. A one-register read of a float is exception 02. Its password lock is not modelled, so protected settings are writable without the password. Its default pulse divisor is not documented, and wattsim uses 0.
- Serial numbers are made up from the unit id (SDM630 26000000 + unit, EM24 `WATTSIM` + six digits). Firmware registers use the EM24 document's example 101Eh.
- Exceptions follow the v1.1b3 order: an unsupported function is 01, a quantity outside the limits or a malformed PDU is 03, an address is 02, and a failing value source or `onWrite` is 04. A write is all or nothing: it is checked whole before anything is stored.
- An unknown unit id answers exception 0Bh (Gateway Target Device Failed to Respond), as a TCP gateway does for a missing serial device, or nothing with `unknownUnit: 'ignore'`. With a single device, unit ids 0 and 255 reach it too, since TCP clients use either to mean "the device at this address".
- An MBAP length outside 2..254 closes the connection, because the byte stream cannot be resynchronised. A non-zero protocol id is dropped without an answer. A client whose unread answers pass 1 MB is disconnected.

`MeterReading` is the contract with `packages/grid`: per-phase voltages (L-N and L-L), currents, neutral current, active/apparent/reactive power and power factor, frequency, import/export kWh in total and per phase, kvarh, and the protective device's state, rating and thermal fraction. Power is positive for import. `deriveReading` fills a partial reading consistently, with 230 V, 50 Hz and pf 1 by default and line-to-line voltages and neutral current from a symmetric 120° phasor system. It is used by the CLI demo and by `liveDevice` unless `derive: false`. The wattsim generic map lays out every quantity as float32 in `QUANTITIES` order, so a new quantity extends the map at its end. The map version register at 0xFE is there to detect that.
