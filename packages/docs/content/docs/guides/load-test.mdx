---
title: Test your CSMS against 1000 chargers
description: A fleet scenario with realistic session lengths and injected faults, run in CI with a JUnit report and Prometheus metrics.
---

This guide builds a fleet of 1000 OCPP 2.0.1 stations where most sit idle and some charge for about 45 minutes, adds a few network faults, and runs it against your CSMS in CI.

## Write the fleet

A `station` block with `for i in FROM..TO` is a template: it runs once per number in the range, and each instance is an independent charge point whose identity is the interpolated name. Save this as `fleet.ws`:

```
wattsim 1

csms "ws://localhost:9000/ocpp"
let size = 1000
let session = normal(45min, 10min)

station "CP-{i}" for i in 1..size {
  version 2.0.1
  serial "SN-{i}"
  heartbeat 5min
  meterInterval 1min
  boot
  choose {
    70%: {
      wait session
    }
    30%: {
      ev plug evse 1 { battery 75kWh soc 15% target 80% }
      authorize "TAG-{i}"
      start evse 1 tag "TAG-{i}"
      wait session
      stop evse 1
      ev unplug evse 1
    }
  }
}
```

- `choose` sends each station down exactly one branch. The weights must add up to 100%.
- `normal(45min, 10min)` is a distribution: every station draws its own session length, so the stops spread out instead of arriving in one burst.
- Both draws come from a random generator seeded by `--seed`, the station name and the statement's position, so the same seed gives the same fleet on every run. Change the seed to get a different, equally reproducible split.

`examples/fleet.ws` in the repository is the same scenario with 200 stations.

## Run it

```sh
wattsim run fleet.ws --csms ws://your-csms:9000/ocpp --virtual --seed 1 --quiet --junit fleet.xml
```

With `--virtual` the run clock jumps forward whenever every station is idle, so the 45 minute sessions finish in seconds of wall time. On a laptop this 1000-station scenario completes in a few seconds against the CSMS simulator; your CSMS's response time sets the pace against a real one. The summary table has one row per station, and `fleet.xml` has one JUnit test case per station.

### Virtual time and a real CSMS

On a virtual clock the stations' timestamps run ahead of your CSMS's wall clock, and their heartbeats and meter values arrive far more often in wall time than the intervals say. That is what you want for functional tests (does every session start, meter and stop correctly?) but it misleads anything in your CSMS that checks timing. For timing-sensitive tests use the wall clock instead:

- `--speed 10` runs every scenario duration ten times faster than real time, and timestamps stay on wall time.
- No flag runs in real time, which is the right setting for soak tests.

## Add faults

Real chargers lose connections and messages. Add rules to the station block, before `boot` so they cover the BootNotification too:

```
  chaos drop out MeterValues every 50 probability 20%
  chaos delay 2s in probability 5%
  at +20min {
    net drop 30s
  }
```

- The first rule drops each station's 50th, 100th, 150th... outgoing MeterValues with a 20% chance each.
- The second holds 5% of the frames your CSMS sends for two seconds before the station sees them.
- `net drop 30s` closes the WebSocket 20 minutes into the scenario and reconnects 30 seconds later. Messages generated meanwhile queue up and are sent in order on reconnect, following the offline behavior of the station's OCPP version.

Probabilities are seeded like the distributions above, so a failing run can be replayed exactly with the same `--seed`. The [chaos reference](/docs/reference/dsl#chaos) lists every fault and trigger.

To assert on what your CSMS does about a fault, add an `expect` after it, for example `expect StatusNotification {status: "Available"} within 30s`. A failed `expect` fails that station's test case and makes `run` exit 1, while the other stations carry on.

## Watch it while it runs

```sh
wattsim run fleet.ws --csms ws://your-csms:9000/ocpp --speed 60 --metrics 9464
```

`--metrics 9464` serves Prometheus metrics on `http://localhost:9464/metrics` for the length of the run:

| Metric | What it counts |
|---|---|
| `wattsim_stations_connected` | Stations with an open WebSocket |
| `wattsim_messages_total` | Frames that crossed the socket, by direction, action and OCPP version |
| `wattsim_transactions_active` | Transactions running |
| `wattsim_energy_wh_total` | Energy metered, in Wh |
| `wattsim_violations_total` | Schema violations detected, by action |
| `wattsim_request_duration_ms` | Time from a station CALL to your CSMS's CALLRESULT or CALLERROR, on the station clock |

## Run it in CI

`wattsim run` exits 0 when every assertion passed, 1 when any failed and 2 when the scenario could not start, so it can gate a pipeline directly. A GitHub Actions step:

```yaml
- uses: oven-sh/setup-bun@v2
  with:
    bun-version: 1.4.4
- run: bun install --frozen-lockfile && bun run build
- run: bun packages/cli/src/index.ts run fleet.ws --csms "$CSMS_URL" --virtual --seed 1 --quiet --junit fleet.xml
```

Keep the seed fixed in CI so a failure reproduces locally with the same command.

## Larger fleets

One process holds 10 000 idle stations. Past that, run the same scenario file in several processes and give each one part of the fleet. There is no coordinator, so the processes can run on one machine or several:

```sh
# four processes, each runs a quarter of the fleet and serves its own /metrics on 9100..9103
for i in 0 1 2 3; do
  wattsim run fleet.ws --csms ws://your-csms:9000/ocpp --quiet --connect-rate 500 --shard $i/4 --metrics-port-base 9100 &
done
wait
```

- `--shard i/n` keeps the stations whose position in the expanded fleet, counted from 0 in file order across every station block, is i modulo n.
- `--ids a..b` keeps the template stations whose loop variable is in a..b, so `--ids 1..5000` and `--ids 5001..10000` split `station "CP-{i}" for i in 1..10000` by identity. A station block without `for` has no loop variable and is skipped. Given both flags, a process keeps what both select.
- `--metrics-port-base 9100` serves `/metrics` on 9100 plus the shard index, one port per process. It replaces `--metrics`.
- `--connect-rate 500` opens at most 500 connections per second. Unpaced, 10 000 sockets open in under a second but stall the event loop for about 250 ms, and a CSMS with a small listen backlog may refuse some of them. On a `--virtual` run the pacing uses the virtual clock, so the run stays deterministic.

Every process expands the whole fleet and checks it for duplicate names before it keeps its part, so each one reports the same scenario errors. Random draws are keyed by station name and `--seed`, never by position, so a station takes the same `choose` branch and session length whichever process runs it. A `barrier` counts the stations of its own process only. A shard that selects nothing exits 0 at once, so a fixed process count works for any fleet size.

- **Lag** is how late a 10 ms interval timer fires: the event loop's responsiveness.
- **Heartbeat jitter** is the difference between the actual and the nominal gap between a station's consecutive Heartbeats.
- **Per-station** figures are (after − before) / stations, where before is the process with the CSMS up and no stations.
- The **scenario** row is the same fleet driven through the scenario interpreter, as `wattsim run` drives it.

`bun scripts/perf.ts run --stations 10000 [--charging 0.1] [--mode virtual] [--via scenario] [--connect-rate 0]` measures one row on your machine; the comment at the top of `scripts/perf.ts` lists every flag.

The interpreter keeps the last 2048 frames of each station whose script contains an `expect`, because `expect` matches against them. A fleet without assertions keeps none: 2000 scenario-driven stations after 6 virtual hours hold 17 KB of heap each, against 205 KB each when every station kept its window. A fleet that asserts on every station grows towards that window, which is another reason to shard it.

### What the machine needs

- **File descriptors.** One per station in the simulator, and one more per station in a CSMS on the same machine. Bun raises the soft limit to the hard limit at start; `scripts/perf.ts` checks the limit and prints the `ulimit -n` to run when it is too low. macOS caps a process at `kern.maxfilesperproc` (92160 on the machine above).
- **Ephemeral ports.** One per station towards one CSMS address. macOS has 16384 (49152 to 65535); `sudo sysctl net.inet.ip.portrange.first=10000` widens the range. A closed socket's port waits 2 × MSL (30 s on macOS) before reuse, so repeated runs back to back can run out.
- **Listen backlog.** `kern.ipc.somaxconn` is 128 on macOS. A CSMS that cannot accept a burst of connects refuses some; `--connect-rate` avoids the burst.

## Run it as a shared server

`wattsim ui` can run where a whole team, or a CI job, reaches it. Anyone who can reach it can run scenarios on that machine, so it sets limits that `wattsim run` does not:

| Flag | Default | Limits |
|---|---|---|
| `--max-stations <n>` | 10000 | Stations a scenario from the browser may expand to. The editor flags a bigger fleet at its `for` range. Shard bigger fleets with `wattsim run --shard` |
| `--max-runs <n>` | 4 | Scenario runs at once. One more gets HTTP 429 |
| `--max-run-time <duration>` | `1h` | How long a real-time run may take, e.g. `30m` or `8h`; `0` for no limit. A virtual run stops after 24 h of virtual time anyway |

Browser scenarios may `import` quirk files and read load profiles from `<data>/scenarios` only. An import that leaves that folder, through `..`, an absolute path or a symlink, is an error and the file is not read. `use plugin` is refused, because it would execute a module from the server's disk; run those scenarios with `wattsim run`.

The API refuses requests that a web page on another origin could send. A POST, PUT, PATCH or DELETE, or the stream's WebSocket upgrade, whose `Origin` header is not the server's own gets 403, and a request body must be `content-type: application/json` (else 415). Scripts that send no `Origin`, such as curl or `wattsim mcp --attach`, are unaffected, but curl needs `-H 'content-type: application/json'` with `-d`. To use the API from a page on another origin, list it with `--allow-origin http://host:port`, comma-separated for several. On a loopback address (the default) the server also refuses any request whose `Host` is not a loopback name, which stops DNS rebinding.

### Docker

```sh
docker build -t wattsim .
docker run -p 7700:7700 -p 7701:7701 -v wattsim-data:/data wattsim
```

The image runs `wattsim ui --host 0.0.0.0 --no-open --data /data --csms-port 7701` as the unprivileged `bun` user, with a health check on `/api/health`. Point external charge points at `ws://<host>:7701/<id>` and the test CSMS checks them; the findings appear on the CSMS page.

There is no authentication. Bound to 0.0.0.0 the server cannot know the names it is reached under, so the loopback `Host` check is off in the container. Before you expose it beyond your machine, put it behind a reverse proxy that adds authentication and keeps the `Host` header, so the server's own-origin check still matches. The origin check compares host and port, not the scheme, so a proxy that terminates TLS works.
